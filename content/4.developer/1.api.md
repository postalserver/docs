The Postal HTTP API allows you to send messages and retrieve message information over HTTPS using JSON. The API is organized as a set of actions; see the [full API documentation](https://apiv1.postalserver.io) for the complete reference.

::callout{icon="i-heroicons-information-circle"}
The examples in this guide use `postal.example.com` as the canonical Postal hostname. A deployment may use another stable hostname, such as `mail.example.com`; replace the hostname in the API URL only. The Postal hostname is unrelated to DNS prefixes such as `dkim`, `postal-verification`, or `psrp`.
::

::callout{icon="i-heroicons-information-circle"}
The current API is intentionally limited. It provides message sending and message-related actions rather than the full Postal management interface. A future v2 API is planned by the project, but no ETA is provided.
::

## General API instructions

- Use HTTPS for API requests.
- `POST` actions send parameters as JSON in the request body with `Content-Type: application/json`.
- Authentication uses the server API key in the `X-Server-API-Key` header.
- Responses are JSON objects with a `status` field and action-specific response data.
- Do not rely on the HTTP status code alone: API-level validation and action errors are commonly returned in a `200 OK` response.

The API overview documents these top-level status values:

| Status | Meaning |
| --- | --- |
| `success` | The action completed successfully. |
| `parameter-error` | The request contains invalid or missing parameters for the action. |
| `error` | The action failed for another application-level reason. |

Action-specific validation errors are described in the individual API action documentation.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
The API key is associated with a Postal Mail Server. The `From` domain used for sending must be authorised for that Mail Server or its Organization. The optional `sender` parameter is subject to the server's Sender Header settings.
::

## Sending a message

There are two send actions:

- [`/api/v1/send/message`](https://apiv1.postalserver.io/controllers/send/message.html) accepts structured message fields as JSON.
- [`/api/v1/send/raw`](https://apiv1.postalserver.io/controllers/send/raw.html) accepts a base64-encoded RFC 2822 message plus the SMTP envelope addresses.

### Structured message

The following example includes every documented top-level parameter. Static JSON is enclosed in a single-quoted shell string, so JSON quotation marks do not need escaping.

```bash
export POSTAL_SERVER_API_KEY='YOUR_SERVER_API_KEY'

curl -sS \
  --request POST \
  'https://postal.example.com/api/v1/send/message' \
  --header "X-Server-API-Key: ${POSTAL_SERVER_API_KEY}" \
  --header 'Content-Type: application/json' \
  --data '{
    "to": [
      "recipient@example.net"
    ],
    "cc": [
      "copy@example.net"
    ],
    "bcc": [
      "archive@example.net"
    ],
    "from": "Example Product <hello@example.com>",
    "sender": "Example Product <sender@example.com>",
    "subject": "Postal API test",
    "tag": "transactional",
    "reply_to": "support@example.com",
    "plain_body": "This is the plain-text body.",
    "html_body": "<p>This is the HTML body.</p>",
    "attachments": [
      {
        "name": "example.txt",
        "content_type": "text/plain",
        "data": "SGVsbG8gZnJvbSBQb3N0YWwu"
      }
    ],
    "headers": {
      "X-Example-Header": "example-value"
    },
    "bounce": false
  }'
```

Parameter requirements and limits:

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `to` | Array | Conditionally | `To` recipients, maximum 50. At least one recipient must be supplied across `to`, `cc`, or `bcc`. |
| `cc` | Array | No | `Cc` recipients, maximum 50. |
| `bcc` | Array | No | `Bcc` recipients, maximum 50. |
| `from` | String | **Yes** | Address used for the `From` header. Its domain must be authorised for the authenticated Mail Server. |
| `sender` | String | No | Address used for the `Sender` header. Use only when the Mail Server permits the Sender Header. |
| `subject` | String | No | Message subject. |
| `tag` | String | No | Postal tag for categorisation/reporting. |
| `reply_to` | String | No | `Reply-To` address. |
| `plain_body` | String | Conditionally | Plain-text body. At least one of `plain_body` or `html_body` must contain content. |
| `html_body` | String | Conditionally | HTML body. At least one of `plain_body` or `html_body` must contain content. |
| `attachments` | Array | No | Message attachments. |
| `headers` | Object | No | Additional message headers. |
| `bounce` | Boolean | No | Marks the message as a bounce when set to `true`. |

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
The full example includes `sender`. To run it unchanged, make sure the authenticated Mail Server permits the Sender Header. Otherwise remove the `sender` field.
::

An attachment object contains these fields:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | String | **Yes** | Filename used for the attachment. |
| `content_type` | String | No | MIME content type, such as `text/plain` or `application/pdf`. |
| `data` | String | **Yes** | Base64-encoded attachment data. |


The API documents validation errors for missing recipients, missing `From`, missing content, and recipient-count limits. ([Send API reference](https://apiv1.postalserver.io/controllers/send/message.html))

::callout{icon="i-heroicons-information-circle"}
A successful API response means that Postal accepted the message for processing. It does not mean that the destination mail server accepted the message or that the message reached the recipient's inbox.
::

### Raw RFC 2822 message

The raw endpoint has three required parameters and one optional parameter:

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `mail_from` | String | **Yes** | SMTP envelope sender address. |
| `rcpt_to` | Array | **Yes** | SMTP envelope recipients. |
| `data` | String | **Yes** | Base64-encoded RFC 2822 message. |
| `bounce` | Boolean | No | Marks the message as a bounce when set to `true`. |

Create the RFC 2822 message as a file first. This keeps the cURL command readable.

```bash
cat > message.eml <<'EOF'
From: hello@example.com
To: recipient@example.net
Subject: Postal raw API test
MIME-Version: 1.0
Content-Type: text/plain; charset=UTF-8

This is a raw RFC 2822 message.
EOF

base64 < message.eml | tr -d '\n' > message.b64
```

For a fixed example, replace `<BASE64_ENCODED_MESSAGE>` below with the value from `message.b64`:

```bash
curl -sS \
  --request POST \
  'https://postal.example.com/api/v1/send/raw' \
  --header "X-Server-API-Key: ${POSTAL_SERVER_API_KEY}" \
  --header 'Content-Type: application/json' \
  --data '{
    "mail_from": "hello@example.com",
    "rcpt_to": [
      "recipient@example.net"
    ],
    "data": "<BASE64_ENCODED_MESSAGE>",
    "bounce": false
  }'
```

For an automated request without editing the JSON, a here-document can safely expand the base64 value:

```bash
encoded_message="$(base64 < message.eml | tr -d '\n')"

curl -sS \
  --request POST \
  'https://postal.example.com/api/v1/send/raw' \
  --header "X-Server-API-Key: ${POSTAL_SERVER_API_KEY}" \
  --header 'Content-Type: application/json' \
  --data @- <<JSON
{
  "mail_from": "hello@example.com",
  "rcpt_to": [
    "recipient@example.net"
  ],
  "data": "${encoded_message}",
  "bounce": false
}
JSON
```

The endpoint expects `data` to contain the base64-encoded RFC 2822 message. The protocol used by the raw-message endpoint is RFC 2822.

## Retrieving a message

Use `GET /api/v1/messages/message`. The required `id` and optional `_expansions` values are query parameters, not a JSON request body. `_expansions` can be supplied as an array of expansion names or as `true` for all available expansions. ([Messages API reference](https://apiv1.postalserver.io/controllers/messages/message.html))

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | Integer | **Yes** | Postal message ID. |
| `_expansions` | Array or Boolean | No | Expansion names, or `true` for all available expansions. |

```bash
curl -sS -G \
  'https://postal.example.com/api/v1/messages/message' \
  --header "X-Server-API-Key: ${POSTAL_SERVER_API_KEY}" \
  --data-urlencode 'id=37171' \
  --data-urlencode '_expansions=true'
```

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
For `GET` actions, put action parameters in the query string. Do not send `id` or `_expansions` as a JSON request body.
::

## API response handling

A successful structured send response includes the Postal message ID and recipient-specific message information. A minimal response can be represented as:

```json
{
  "status": "success",
  "time": 0.02,
  "flags": {},
  "data": {
    "message_id": "xxxx",
    "messages": {}
  }
}
```

Inspect `status` and the action-specific `data` for application-level errors. The API overview documents `success` and `error` status values. HTTP `200 OK` is commonly used for successful actions and application-level failures; transport/server failures such as `500` or `503` should be handled separately. ([API overview](https://apiv1.postalserver.io/))
