Postal keeps two things strictly apart: the **Postal installation** and the **domains Postal sends mail for**.

For example:

```text
Postal installation:
    postal.example.com

Sending domains:
    example.com
    transactional.example.com
    customer-example.com
```

A sending domain is the domain in the visible `From:` address of messages sent through Postal.

::callout{icon="i-heroicons-information-circle"}
The Postal hostname does not have to be the sending domain. This guide uses `postal.example.com` as its canonical example, but a deployment may use any stable hostname, such as `mail.example.com`. The hostname is independent of `dkim_identifier`, `domain_verify_prefix` and `custom_return_path_prefix`, so never infer DNS prefixes or sending-domain records from the Postal hostname.
::

## Part 1: Configure sending domains in Postal

Follow this part from top to bottom to take a new domain from "added" to "production-ready". Everything here is specific to Postal: which settings drive which records, and what Postal's DNS checker expects to see.

### DNS records at a glance

For a sending domain such as `example.com`, Postal works with the following records. Each is explained in its own section below.

| Purpose | Record name | Type | Value | Postal setting |
| --- | --- | --- | --- | --- |
| Domain verification | `example.com` | TXT | `postal-verification <TOKEN>` | `dns.domain_verify_prefix` |
| SPF | `example.com` | TXT | `v=spf1 include:spf.postal.example.com -all` | `dns.spf_include` |
| DKIM | `<dkim_identifier>-<ID>._domainkey.example.com` | TXT | Generated by Postal for the domain | `dns.dkim_identifier` |
| Return Path | `psrp.example.com` | CNAME | `rp.postal.example.com.` | `dns.custom_return_path_prefix`, `dns.return_path_domain` |
| DMARC | `_dmarc.example.com` | TXT | Your policy (see [DMARC](#dmarc)) | None. DNS only. |
| MX (optional) | `example.com` | MX | `10 postal.example.com.` | `dns.mx_records` |

### Organization and Mail Server

In the Postal web UI, create an Organization, then add one or more Mail Servers inside it.

A simple deployment looks like this:

```text
My Company
└── Transactional
    └── example.com
```

A Postal domain can be owned by an Organization or directly by a Mail Server. A Mail Server can authenticate and send with any verified domain that belongs to that server or to its Organization.

::callout{icon="i-heroicons-information-circle"}
Choose one ownership model per domain, based on how widely the domain should be shared. Avoid creating duplicate domain objects at both Organization and Mail Server level unless the duplication is intentional.
::

### Add the sending domain

Add the exact domain you plan to use in the `From:` address.

For example:

```text
example.com
```

or:

```text
transactional.example.com
```

A parent domain and a sending subdomain are separate Postal domains. Each is verified independently.

### Domain verification

Postal supports DNS-based and email-based domain verification. DNS verification is easier to automate and is the method described here.

With the default configuration:

```yaml
dns:
  domain_verify_prefix: postal-verification
```

Postal builds a verification TXT value in this form:

```text
postal-verification <TOKEN>
```

For the domain `example.com`, publish:

```dns
example.com.    TXT    "postal-verification <TOKEN>"
```

If you customize the prefix:

```yaml
dns:
  domain_verify_prefix: dkim-verification
```

the value changes accordingly:

```dns
example.com.    TXT    "dkim-verification <TOKEN>"
```

::callout{icon="i-heroicons-exclamation-triangle"}
`domain_verify_prefix` is part of the TXT **value**, not a DNS hostname. Do not create `postal-verification.example.com` or `dkim-verification.example.com` for this check.
::

Postal queries the TXT records of the exact domain configured in Postal and looks for the generated verification string.

### SPF

The sending domain must publish an SPF record that contains the Postal SPF include configured in `dns.spf_include`.

For example:

```dns
example.com.    TXT    "v=spf1 include:spf.postal.example.com -all"
```

If another provider already sends mail for the domain, merge all providers into **one** SPF policy instead of publishing several independent records:

```dns
example.com.    TXT    "v=spf1 include:_spf.example-provider.com include:spf.postal.example.com -all"
```

::callout{icon="i-heroicons-exclamation-triangle"}
Publish exactly one SPF record per domain, and keep the full evaluation chain within the limit of 10 DNS lookups. Switch to `-all` only after every legitimate sender is included.
::

#### Migration mode

While you are migrating or validating a new setup, the policy can end in a soft fail:

```text
~all
```

Once every legitimate sender has been verified, tighten it to a hard fail:

```text
-all
```

Whichever ending you choose, keep the SPF evaluation chain below the DNS lookup limit. Avoid unnecessary nested `include` chains and deprecated mechanisms such as `ptr`.

::callout{icon="i-heroicons-information-circle"}
**What Postal checks:** the DNS checker requires a valid SPF record that contains the configured `spf_include`. It does not require `~all` or `-all` specifically.
::

For every mechanism, qualifier, modifier and limit, see the [SPF reference](#spf-reference).

### DKIM

Postal generates a unique DKIM selector for each domain.

With:

```yaml
dns:
  dkim_identifier: postal
```

an example selector is:

```text
postal-ABCDEF
```

and the matching record name is:

```text
postal-ABCDEF._domainkey.example.com
```

If you configure:

```yaml
dns:
  dkim_identifier: dkim
```

the selector uses the `dkim` prefix instead, for example:

```text
dkim-ABCDEF._domainkey.example.com
```

Always publish the exact selector and TXT value that Postal generates for that domain. Do not use the output of `postal default-dkim-record` for a sending domain; that command produces Postal's global record, not a per-domain one.

::callout{icon="i-heroicons-exclamation-triangle"}
Do not replace Postal's generated selector with a generic `dkim._domainkey.example.com` record. The selector carries a per-domain identifier.
::

Postal includes `t=s` in the DKIM record it generates. This flag requires the signature's signing identity (`i=`) to match the signing domain (`d=`) exactly, so the key cannot be used to sign on behalf of subdomains.

The current Postal source generates 1024-bit RSA DKIM keys. This is an implementation detail of the current application, and it is worth weighing against your own cryptographic requirements.

::callout{icon="i-heroicons-information-circle"}
**Ed25519 note:** Postal currently generates RSA DKIM keys. Publishing an Ed25519 DKIM record will not make Postal sign with it; Ed25519 would require a different signing implementation or an external signing layer.
::

#### DKIM signing behavior

Postal signs with the domain-specific DKIM key when the domain's stored DKIM status is `OK`. If the domain is in any other state, the current signing code falls back to the global Postal signing key and the configured `return_path_domain`.

::callout{icon="i-heroicons-exclamation-triangle"}
Before sending production traffic, confirm that Postal reports the expected DKIM DNS record as `OK`. A domain that has not passed the DKIM check may be signed with Postal's fallback identity instead of the sending domain's own DKIM identity, which breaks DMARC alignment through DKIM.
::

DKIM has no equivalent of SPF's `~all` or `-all`. A signature either verifies or it does not; DMARC decides what happens to a message that fails to produce an aligned pass.

::callout{icon="i-heroicons-information-circle"}
**Rotating keys:** publish a new selector and key before removing the old selector. Keep the old key available long enough for previously sent messages to age out of receiving systems' caches. Never overwrite an active selector in place unless you are deliberately managing that transition.
::

Tag-by-tag detail is in the [DKIM reference](#dkim-reference).

### Return Path

Postal derives a Return Path hostname from the sending domain and `dns.custom_return_path_prefix`.

With:

```yaml
dns:
  custom_return_path_prefix: psrp
  return_path_domain: rp.postal.example.com
```

and the sending domain:

```text
example.com
```

Postal derives:

```text
psrp.example.com
```

Create the record:

```dns
psrp.example.com.    CNAME    rp.postal.example.com.
```

For the sending domain:

```text
transactional.example.com
```

the derived hostname becomes:

```text
psrp.transactional.example.com
```

::callout{icon="i-heroicons-exclamation-triangle"}
Do not move a derived Return Path record to the parent domain. The hostname is built from the exact sending-domain name.
::

The CNAME hands every DNS lookup for `psrp.example.com` over to `rp.postal.example.com`. SPF checks and bounce routing for the Return Path domain are therefore answered by the records published at the CNAME target. See the DNS configuration page for the records the Return Path domain itself needs, and the [Return Path and bounce handling reference](#return-path-and-bounce-handling-reference) for how the mechanism works.

### DMARC

DMARC is published in DNS only. There is no `postal.yml` setting for the DMARC policy.

#### Production policy

For a hardened production configuration, move to `p=reject` once every legitimate sender has been verified. During migration, `p=none` provides monitoring without enforcement, and `p=quarantine` asks receivers to treat failing messages as suspicious. These are migration stages, not equivalent end states.

Publish the record for the sending domain:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

What each tag does:

- `p=reject` asks receivers to reject messages that fail DMARC for the policy domain.
- `sp=reject` applies the same policy to subdomains that do not publish their own DMARC record.
- `adkim=s` requires strict DKIM identifier alignment.
- `aspf=r` allows relaxed SPF identifier alignment.
- `rua` requests aggregate DMARC reports.

::callout{icon="i-heroicons-information-circle"}
**About `pct`:** older guides, and earlier versions of this page, include `pct=100`. The DMARC revision published in May 2026 (RFC 9989) retired the `pct` tag. Omit it. Receivers that still implement the previous specification treat a missing `pct` as 100, so the behavior is identical. See [DMARC reference](#dmarc-reference) for the full tag list.
::

::callout{icon="i-heroicons-information-circle"}
If the `rua` address belongs to a different organizational domain, that reporting domain must explicitly authorize reports for the sending domain. Using a mailbox on the same domain, such as `dmarc@example.com`, keeps the setup simple.
::

::callout{icon="i-heroicons-information-circle"}
`aspf=r` is deliberate and matches Postal's standard Return Path design. A message sent with `From: user@example.com` typically uses an envelope return path on a subdomain such as `psrp.example.com`. Relaxed SPF alignment lets those two identifiers align at the organizational-domain level, whereas strict alignment fails whenever the domains differ by a subdomain.
::

When Postal has a working domain-specific DKIM record, the DKIM signing domain is the sending domain itself, so strict DKIM alignment (`adkim=s`) is safe to use.

#### DMARC migration modes

Start a new domain in monitoring mode:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=none; sp=none; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

Move to intermediate enforcement:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=quarantine; sp=quarantine; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

Finish at the hardened policy:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

::callout{icon="i-heroicons-information-circle"}
`p=none` and `p=quarantine` are useful stepping stones, not equivalents of `p=reject`. Review your aggregate reports before moving a production domain to rejection. The [DMARC reference](#dmarc-reference) explains the newer `t` testing flag, which offers a safer way to trial a stricter policy.
::

### HELO/EHLO hostname

The `dns.helo_hostname` setting controls the hostname Postal announces in the `HELO` or `EHLO` command when it connects to remote SMTP servers for outbound delivery.

For a standard production deployment, use the same public fully qualified domain name (FQDN) for `dns.helo_hostname` and `postal.smtp_hostname`:

```yaml
postal:
  smtp_hostname: postal.example.com

dns:
  helo_hostname: postal.example.com
```

This keeps the SMTP hostname and the SMTP session identity aligned:

```text
SMTP hostname:  postal.example.com
HELO/EHLO:      postal.example.com
```

Postal treats these as two separate settings. A different `dns.helo_hostname` intentionally overrides `postal.smtp_hostname`, and leaving `dns.helo_hostname` empty lets Postal apply its normal fallback behavior. Matching the two values is therefore a **recommended production configuration**, not a hard schema requirement.

::callout{icon="i-heroicons-information-circle"}
**Keep `postal.smtp_hostname` and `dns.helo_hostname` identical unless you have a documented reason to run a separate outbound SMTP identity.** Changing them independently makes DNS, TLS certificates, reverse DNS and SMTP diagnostics harder to reason about.
::

::callout{icon="i-heroicons-check-circle"}
**Recommended production state:** the outbound SMTP IP has a `PTR` record pointing to the hostname used in `HELO`/`EHLO`, and that hostname has matching `A`/`AAAA` records pointing back to the same outbound IP. This two-way match is called FCrDNS; see the [reverse DNS and FCrDNS reference](#reverse-dns-and-fcrdns-reference) for the full explanation.
::

#### TLS certificate and SMTP identity

When SMTP TLS is enabled, the certificate presented by the SMTP service should contain the hostname that remote systems use as the SMTP endpoint. Keeping `postal.smtp_hostname` and `dns.helo_hostname` aligned with the public SMTP certificate name reduces hostname-mismatch problems during TLS negotiation.

If you deliberately use a separate `helo_hostname`, configure and verify its DNS and certificate identity as part of the same deployment. Treat it as a real identity, not a cosmetic value.

::callout{icon="i-heroicons-exclamation-triangle"}
**Never use `localhost`, a container hostname, an internal-only name or an unresolvable hostname for outbound HELO/EHLO.** The value is presented to external SMTP servers and must identify the public sending system.
::

#### When can the values differ?

A different `dns.helo_hostname` makes sense only when you intentionally operate a separate outbound SMTP identity. For example:

```yaml
postal:
  smtp_hostname: mail.example.com

dns:
  helo_hostname: outbound.example.com
```

In this configuration, `outbound.example.com` becomes the identity announced in the SMTP `HELO`/`EHLO` command. Its forward DNS, reverse DNS, TLS certificate and outbound source IP must all be configured consistently.

::callout{icon="i-heroicons-information-circle"}
**Advanced configuration:** a different HELO hostname is supported, but it must be deliberate. Never change only the HELO value while leaving the corresponding DNS or certificate identity untouched.
::

#### Operational verification

Before production, verify the complete forward and reverse chain:

```bash
dig A postal.example.com
dig AAAA postal.example.com
dig -x 203.0.113.10
```

The forward lookup should return the public outbound SMTP IP, and the reverse lookup should return the hostname Postal presents in `HELO`/`EHLO`.

For a single IPv4 address, the expected relationship is:

```text
HELO/EHLO:   postal.example.com
PTR/rDNS:    203.0.113.10 → postal.example.com
Forward DNS: postal.example.com → 203.0.113.10
```

### MX and inbound mail

MX is an independent architectural decision. Whether Postal receives mail for a domain has no bearing on whether it can send for it.

#### Sending only

If another provider already receives mail for the sending domain, keep its existing MX records. Postal works as an outbound sending platform without becoming the inbound mail server.

#### Sending and receiving

If Postal should also receive mail for the sending domain, publish an MX record that points to one of the hostnames configured in `dns.mx_records`.

For a single-node installation:

```yaml
dns:
  mx_records:
    - postal.example.com
```

and:

```dns
example.com.    MX    10 postal.example.com.
```

For a multi-node installation, use the actual MX hostnames configured in `dns.mx_records`.

::callout{icon="i-heroicons-exclamation-triangle"}
Changing MX changes the inbound mail path. Never replace an existing production MX record just because Postal is configured for outbound delivery.
::

Postal's DNS checker reports a missing MX as `Missing`. If MX records exist but do not include every configured Postal MX host, the check may be reported as invalid. See the DNS configuration page for how `dns.mx_records` relates to Postal's checks, and the [MX reference](#mx-reference) for how MX resolution works.

### Sending subdomains

A sending subdomain is an independent Postal domain with its own complete set of records.

For example, the domain:

```text
transactional.example.com
```

may use:

```dns
transactional.example.com.    TXT    "postal-verification <TOKEN>"
transactional.example.com.    TXT    "v=spf1 include:spf.postal.example.com -all"
dkim-ABCDEF._domainkey.transactional.example.com.    TXT    "v=DKIM1; t=s; h=sha256; p=<PUBLIC_KEY>;"
psrp.transactional.example.com.    CNAME    rp.postal.example.com.
_dmarc.transactional.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

Every record belongs to the exact sending-domain namespace it protects.

### DNS hierarchy rule

For a sending domain such as `example.com`, Postal expects:

```text
Verification:
    TXT on example.com

SPF:
    TXT on example.com

DKIM:
    <selector>._domainkey.example.com

Return Path:
    psrp.example.com

DMARC:
    _dmarc.example.com
```

For a sending subdomain such as `transactional.example.com`, every derived name moves with that exact domain.

Never move records to a parent domain because the shorter name looks tidier.

### Production checklist

Before enabling production traffic for a sending domain, verify each of the following:

```text
[ ] The domain exists in the intended Organization or Mail Server.
[ ] Domain verification is successful.
[ ] SPF is a single record and contains the configured Postal SPF include.
[ ] SPF uses -all in the final hardened policy.
[ ] The DKIM record exactly matches the record generated by Postal.
[ ] Postal reports the domain DKIM check as OK.
[ ] The Return Path CNAME resolves to the configured Return Path domain.
[ ] DMARC is published, with a rua address that receives aggregate reports.
[ ] DMARC is eventually enforced with p=reject.
[ ] All legitimate sending sources are covered by SPF or DKIM.
[ ] postal.smtp_hostname and dns.helo_hostname are public FQDNs (identical unless deliberately different).
[ ] The outbound IP has a PTR record that matches the HELO/EHLO hostname, and that hostname resolves back to the same IP.
[ ] Existing inbound MX has not been changed accidentally.
[ ] A real message has been tested and SPF, DKIM and DMARC results are as expected.
```

## Part 2: Email technology reference

Part 1 tells you *what* to publish. This part explains *why* each record exists, which parameters it accepts and how receiving systems interpret it. Use it to audit a record, choose between policy variants or diagnose a failing check.

Postal-specific behavior is called out in notes. Everything else describes the underlying standards and applies to any mail platform.

### Email identities: From, MAIL FROM and HELO

A single message carries several different "sender" identities, and each authentication mechanism looks at a different one. Confusing them is the most common source of SPF, DKIM and DMARC problems.

| Identity | Where it appears | Used by | Controlled in Postal by |
| --- | --- | --- | --- |
| **Visible sender** (`RFC5322.From`, the *Author Domain*) | The `From:` header shown to the recipient | DMARC: every other identity must align with it | The sending application |
| **Envelope sender** (`RFC5321.MailFrom`) | The SMTP `MAIL FROM` command, saved as the `Return-Path:` header on delivery | SPF and bounce handling | The Return Path domain |
| **HELO/EHLO name** | The SMTP `HELO` or `EHLO` command | SPF for empty senders, reverse-DNS and reputation checks | `dns.helo_hostname` |
| **DKIM signing domain** | The `d=` tag of the `DKIM-Signature` header | DKIM, and DMARC alignment | The per-domain DKIM key |

The visible sender and the envelope sender may use different domains, and in a normal Postal setup they do:

```text
From:       hello@example.com
MAIL FROM:  bounces@psrp.example.com
```

The envelope address is part of the delivery envelope and is not normally displayed by mail clients.

::callout{icon="i-heroicons-information-circle"}
**DMARC alignment matters:** SPF authenticates the `MAIL FROM` domain, and DKIM authenticates the domain in the `d=` value. DMARC then checks whether at least one of those authenticated domains is aligned with the domain in the `From:` header.
::

Bounce messages (delivery status notifications) are sent with an **empty** envelope sender, written `MAIL FROM:<>`. This is deliberate: it stops bounces from generating bounces of their own. When the envelope sender is empty, SPF evaluates the HELO/EHLO name instead, using the mailbox `postmaster@<HELO name>`. This is one reason the HELO hostname must be a real, resolvable public name.

### DNS record fundamentals

Every technology in this part is published as ordinary DNS records. A few DNS rules apply to all of them:

- **TXT values are quoted strings.** A single string is limited to 255 characters. Longer values, such as 2048-bit DKIM keys, are split into several quoted strings inside one record. Receivers join the strings **without inserting spaces**, so keep separators such as `; ` exactly where the format needs them. Most DNS providers split long values automatically.
- **One policy record per name.** Publishing two SPF records, two DMARC records or two TLS-RPT records at the same name causes those mechanisms to be ignored or to fail.
- **A CNAME cannot share its name with other records.** Never place a CNAME at a name that also carries TXT, MX or A records, and never at the zone apex.
- **Underscore labels are protocol labels.** Names such as `_dmarc`, `_domainkey`, `_mta-sts`, `_smtp._tls` and `_bimi` are reserved for the mechanism that owns them and are not hostnames.
- **Mind the trailing dot and provider auto-completion.** Many DNS panels append the zone name automatically. If you enter `_dmarc.example.com` into a panel that appends `example.com`, you create `_dmarc.example.com.example.com`. When in doubt, enter only the relative label (`_dmarc`) or check the result with `dig`.
- **TTL and propagation.** A low TTL (for example 300 seconds) is useful while testing. Raise it once the records are stable.

To inspect any record from the command line:

```bash
dig TXT example.com +short
dig TXT _dmarc.example.com +short
dig TXT postal-ABCDEF._domainkey.example.com +short
```

### SPF reference

The Sender Policy Framework (SPF, RFC 7208) lets a domain publish which servers may send mail using that domain in the SMTP envelope.

#### How SPF works

When a receiving server accepts a connection, it takes the connecting IP address and the envelope sender domain, looks up the domain's SPF record and evaluates its terms **from left to right**. The first term that matches decides the result. If nothing matches, the result is `neutral`.

SPF evaluates the envelope sender (or the HELO name when the sender is empty). It never looks at the visible `From:` header. That is why DMARC adds an alignment check on top of it.

#### SPF record anatomy

```dns
example.com.    TXT    "v=spf1 ip4:203.0.113.0/24 include:spf.postal.example.com -all"
```

| Part | Meaning |
| --- | --- |
| `v=spf1` | Version tag. Required, and must come first. |
| `ip4:203.0.113.0/24` | A mechanism: authorizes an IPv4 range. |
| `include:spf.postal.example.com` | A mechanism: also authorizes whatever that domain's SPF record authorizes. |
| `-all` | The closing term: what to do with everyone else. |

Each term is a mechanism with an optional one-character qualifier in front of it, such as `-all` or `~include:...`. Mechanism and modifier names are case-insensitive.

#### SPF qualifiers

A qualifier is a one-character prefix that sets the result returned when a mechanism matches. If you omit it, `+` is assumed.

| Qualifier | Result | Meaning |
| --- | --- | --- |
| `+` (default) | `pass` | The sender is authorized. |
| `-` | `fail` | The sender is explicitly **not** authorized (hard fail). |
| `~` | `softfail` | The sender is probably not authorized, but the domain owner does not want a hard rejection (soft fail). |
| `?` | `neutral` | The domain makes no statement about this sender. |

#### SPF mechanisms

| Mechanism | Example | Matches when | Counts toward the 10-lookup limit |
| --- | --- | --- | --- |
| `all` | `-all` | Always. Place it last: terms after it are never evaluated. | No |
| `ip4` | `ip4:203.0.113.10`, `ip4:203.0.113.0/24` | The sending IPv4 address equals the address or falls in the range. | No |
| `ip6` | `ip6:2001:db8::/32` | The sending IPv6 address falls in the range. | No |
| `a` | `a`, `a:mail.example.com`, `a:mail.example.com/24` | The sending IP matches an `A`/`AAAA` record of the domain (optionally widened with a CIDR prefix). | Yes (1) |
| `mx` | `mx`, `mx:example.com` | The sending IP matches an address of one of the domain's MX hosts. At most 10 MX hosts are evaluated. | Yes (1) |
| `include` | `include:spf.postal.example.com` | The referenced domain's policy evaluates to `pass`. A `fail` or `softfail` inside the include does **not** propagate; it simply counts as no match. | Yes (1, plus any nested lookups) |
| `exists` | `exists:%{i}._spf.example.com` | The macro-expanded name has an `A` record. Used for advanced, per-IP allow-lists. | Yes (1) |
| `ptr` | `ptr` | Reverse-DNS based match. **Deprecated:** slow, unreliable and discouraged by RFC 7208. Do not use it. | Yes |

#### SPF modifiers

Modifiers are `name=value` terms. Unlike mechanisms, they do not take a qualifier and each may appear at most once.

| Modifier | Example | Purpose |
| --- | --- | --- |
| `redirect` | `v=spf1 redirect=_spf.example.com` | Replaces this record with the policy of another domain when no mechanism has matched. The redirect target's result becomes the final result. Ignored if the record contains `all`. Counts as a DNS lookup. |
| `exp` | `exp=explain._spf.example.com` | Points to a TXT record whose text is returned to the sender as the explanation for a `fail`. Rarely used. |
| Unknown modifiers | `foo=bar` | Ignored, which allows future extensions. |

Use `include` when you add another sender to your own policy. Use `redirect` when a domain hands over its **entire** policy to another domain, for example a set of parked domains that all share one record.

#### SPF results

| Result | Meaning | Typical receiver reaction |
| --- | --- | --- |
| `pass` | The sending IP is authorized. | Counts as an SPF pass for DMARC (if aligned). |
| `fail` | The IP is explicitly not authorized (`-`). | May reject during the SMTP session or mark as spam. |
| `softfail` | The IP is probably not authorized (`~`). | Usually accepts but treats the message as suspicious. |
| `neutral` | The domain makes no assertion (`?`, or no term matched). | Treated much like "no SPF". |
| `none` | No SPF record was found for the domain. | No SPF signal available. |
| `temperror` | A temporary DNS error prevented evaluation. | May defer the message with a 4xx reply so the sender retries. |
| `permerror` | The record is broken: bad syntax, more than one SPF record, or a limit exceeded. | Treated as a failed policy. All mail from the domain can be affected. |

DMARC only credits SPF when the result is `pass` **and** the authenticated domain is aligned with the `From:` domain.

#### Choosing the closing policy

| Ending | Result for unlisted senders | Use it when |
| --- | --- | --- |
| `-all` | `fail` | Production, once every legitimate sender is listed. |
| `~all` | `softfail` | Migration and validation, or when much of your mail is forwarded. |
| `?all` | `neutral` | Almost never. It expresses no policy and gives no protection. |
| `+all` | `pass` | **Never.** It authorizes the entire internet to send as your domain. |
| `redirect=<domain>` (no `all`) | The target domain's policy | The domain intentionally shares another domain's SPF policy. |
| No closing term at all | `neutral` | Avoid. The default outcome is a no-op. |

#### SPF limits and pitfalls

- **10 DNS lookups maximum.** The terms `include`, `a`, `mx`, `ptr`, `exists` and `redirect` each count, including those inside nested includes. Exceeding 10 produces `permerror`, and every message fails SPF. `ip4`, `ip6` and `all` are free.
- **2 void lookups.** A lookup that returns nothing (`NXDOMAIN` or an empty answer) is a "void" lookup. RFC 7208 recommends failing evaluation after two of them, so stale includes for defunct providers can break a whole policy.
- **One SPF record per name.** Two `v=spf1` records at the same name produce `permerror`. Merge them.
- **TXT only.** The dedicated SPF record type (99) is obsolete. Publish SPF as TXT.
- **Keep it compact.** Large records risk exceeding UDP response sizes and 255-character string limits, and encourage lookup-limit problems. Prefer `ip4`/`ip6` ranges over stacking many `include` mechanisms.
- **Avoid `ptr`.** It is deprecated and slow.
- **SPF checks the connecting IP only.** It does not survive forwarding, because a forwarder connects from its own IP address.

::callout{icon="i-heroicons-information-circle"}
**Forwarding and `-all`:** a receiver may evaluate SPF early in the SMTP conversation and reject on a hard fail before it ever reads the message or its DMARC policy. Such rejections never appear in DMARC aggregate reports, and a message with a valid, aligned DKIM signature can be refused purely because of the SPF result. Domains whose recipients often forward mail can combine `~all` with DMARC enforcement, since DMARC still catches spoofed mail through alignment. Both approaches are valid; choose deliberately.
::

### DKIM reference

DomainKeys Identified Mail (DKIM, RFC 6376) lets the sending system attach a cryptographic signature to a message. The receiver fetches the matching public key from DNS and verifies that the signed parts of the message were not altered and that the signing domain authorized the message.

#### How DKIM works

1. The sending system hashes the message body and a chosen set of headers.
2. It signs that hash with a **private key** and adds the result as a `DKIM-Signature` header. The header names the signing domain (`d=`) and the **selector** (`s=`).
3. The receiver builds the DNS name `<selector>._domainkey.<domain>` and fetches the **public key** from that TXT record.
4. The receiver recomputes the hashes and checks the signature.

Because the selector is part of the DNS name, one domain can publish many keys at once. This is what makes rotation and multiple senders practical.

#### DKIM key record tags

The TXT record at `<selector>._domainkey.<domain>` is a list of `tag=value` pairs separated by semicolons.

| Tag | Required | Values | Meaning |
| --- | --- | --- | --- |
| `v` | Recommended | `DKIM1` | Record version. If present, it must come first. |
| `k` | No | `rsa` (default), `ed25519` | Key type. |
| `p` | **Yes** | Base64 public key, or empty | The public key. **An empty `p=` means the key has been revoked.** |
| `h` | No | `sha256`, `sha1`, or a colon-separated list | Hash algorithms the key may be used with. Default: all. Use `h=sha256`; SHA-1 is obsolete. |
| `s` | No | `*` (default) or `email` | Service type the key applies to. `*` means any service. |
| `t` | No | `y`, `s`, or `y:s` | Flags. `y` means the domain is **testing** DKIM, and receivers should not treat failures as decisive. `s` means the signature's `i=` identity must equal `d=` exactly, so subdomain identities are not allowed. |
| `n` | No | Free text | Human-readable notes. Ignored by verifiers; better left out. |

The record Postal generates has this shape:

```dns
postal-ABCDEF._domainkey.example.com.    TXT    "v=DKIM1; t=s; h=sha256; p=<PUBLIC_KEY>;"
```

#### DKIM-Signature header tags

You do not publish these; the sender adds them. Knowing them helps when reading message headers.

| Tag | Required | Meaning |
| --- | --- | --- |
| `v` | Yes | Signature version. Always `1`. |
| `a` | Yes | Signing algorithm, for example `rsa-sha256`. |
| `d` | Yes | Signing domain. This is the identifier DMARC aligns with the `From:` domain. |
| `s` | Yes | Selector. Combined with `d`, it locates the public key. |
| `h` | Yes | Colon-separated list of signed header fields. It must include `From`. |
| `bh` | Yes | Hash of the canonicalized message body. |
| `b` | Yes | The signature itself. |
| `c` | No | Canonicalization as `header/body`. Default: `simple/simple`. |
| `i` | No | Agent or User Identifier (AUID). Defaults to `@` plus the `d=` domain. |
| `t` | Recommended | Signature timestamp (Unix time). |
| `x` | No | Signature expiration time. Verifiers must reject expired signatures. |
| `l` | No | Number of body bytes covered by the signature. **Avoid it:** it lets an attacker append content to a signed message. |
| `q` | No | Key lookup method. Only `dns/txt` is defined, and it is the default. |
| `z` | No | Copy of the original headers, for diagnostics only. |

#### DKIM algorithms and key length

| Item | Status |
| --- | --- |
| `rsa-sha256` | Standard and universally supported. The baseline choice. |
| `rsa-sha1` | Obsolete. RFC 8301 forbids signing with it and verifiers must not accept it. |
| `ed25519-sha256` | Defined in RFC 8463. Compact keys and signatures, but not supported by every verifier, so it is usually published **alongside** an RSA signature rather than instead of it. |
| RSA key size | RFC 8301: signers must use at least 1024 bits, and verifiers must not accept anything shorter. **2048 bits is recommended.** |

A 2048-bit RSA public key exceeds 255 characters and must be published as several strings inside one TXT record. DNS providers normally handle this automatically.

::callout{icon="i-heroicons-information-circle"}
**Postal note:** the current Postal implementation generates 1024-bit RSA keys and signs with RSA only. See the DKIM section in Part 1 for the implications and the Ed25519 caveat.
::

#### DKIM canonicalization

Canonicalization decides how tolerant the signature is to small changes made in transit, such as re-wrapped headers or trimmed whitespace. It is set separately for headers and body in the `c=` tag.

| Mode | Headers | Body |
| --- | --- | --- |
| `simple` | No changes allowed. Even whitespace changes break the signature. | Ignores only trailing empty lines. |
| `relaxed` | Lowercases header names, unfolds lines and collapses whitespace. | Collapses whitespace within lines and ignores trailing whitespace and empty lines. |

`relaxed/relaxed` is the most resilient choice in practice. `simple/simple` is the default when `c=` is omitted, and it is the most likely to break when an intermediate system reformats the message.

#### DKIM selectors, rotation and revocation

- **Selectors** namespace keys. Use a distinct selector per sending system or per key generation.
- **Rotate deliberately.** Publish the new selector first, switch signing to it, and remove the old selector only after previously sent mail has aged out of receiver caches. Many operators rotate keys periodically as routine hygiene.
- **Revoke by emptying `p`.** Publishing `v=DKIM1; p=` tells verifiers the key is withdrawn. Keep the empty record in place for a while rather than deleting it, so verifiers get a definitive answer.
- **Delegating a selector** to a third-party provider with a CNAME is valid, and lets the provider rotate keys without touching your DNS.
- **Test mode:** `t=y` signals that DKIM is still being validated. Remove it once signing is confirmed.

#### DKIM verification results

| Result | Meaning |
| --- | --- |
| `pass` | A signature was found, the key was retrieved and the signature is valid. |
| `fail` | The signature was checked and did not validate: the message body or a signed header was modified, or the wrong key was used. |
| `neutral` | The signature is malformed or otherwise unusable, without being a clear failure. |
| `policy` | The signature was not accepted because of a local receiver policy, for example a key that is too short. |
| `temperror` | A temporary problem, usually DNS, prevented verification. Retrying may succeed. |
| `permerror` | A permanent problem, such as a missing or malformed key record. |
| `none` | The message carries no DKIM signature. |

A message can carry several signatures. DMARC passes on DKIM if **any** valid signature has a `d=` domain aligned with the `From:` domain.

#### DKIM best practices

- Always include `From` in the signed headers. Signing additional headers such as `Subject`, `Date` and `To` strengthens the signature.
- Sign each header field name one extra time (over-signing) to prevent attackers from appending duplicate headers after signing.
- Do not use the `l=` body-length tag.
- Sign with a `d=` domain that matches the `From:` domain, so DMARC alignment is guaranteed even when SPF cannot align.
- Verify the published key after every change:

```bash
dig TXT postal-ABCDEF._domainkey.example.com +short
```

### DMARC reference

Domain-based Message Authentication, Reporting and Conformance (DMARC) ties SPF and DKIM to the visible `From:` domain. It lets the domain owner publish a policy for messages that fail authentication and request reports about how the domain is being used.

::callout{icon="i-heroicons-information-circle"}
**Standards status:** DMARC was first published as RFC 7489, an informational document. In May 2026 the IETF replaced it with three Standards Track documents: **RFC 9989** (the core protocol), **RFC 9990** (aggregate reporting) and **RFC 9991** (failure reporting). Records still begin with `v=DMARC1`, so existing records keep working. Receivers adopt the changes at their own pace, so publish records that behave sensibly under both the old and the new rules.
::

What changed in RFC 9989:

| Change | Detail |
| --- | --- |
| **Added** `np` | A separate policy for non-existent subdomains. |
| **Added** `t` | A binary testing flag that replaces percentage-based rollout. |
| **Added** `psd` | Marks public suffix domains. Relevant to registries, not to ordinary senders. |
| **Retired** `pct`, `rf`, `ri` | Removed from the core specification. Current records should omit them. |
| **New discovery method** | Organizational domains are found with a DNS "tree walk" rather than the Public Suffix List. |
| **Split reporting** | Aggregate and failure reporting moved into their own documents. |

#### DMARC record syntax

A DMARC record is a single TXT record published at `_dmarc.<domain>`:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

The syntax rules receivers apply:

- `v=DMARC1` must be the **first** tag and is case-sensitive. Otherwise the whole record is ignored.
- Tags are separated by semicolons. Whitespace around separators is allowed.
- Unknown tags are ignored, and tags with syntax errors fall back to their defaults.
- If a name returns **more than one** DMARC record, receivers discard all of them, and your policy is not applied. Publish exactly one.
- A TXT record split into several strings is joined in order before parsing.

#### DMARC tag reference

| Tag | Default | Values | Meaning |
| --- | --- | --- | --- |
| `v` | none (required) | `DMARC1` | Version. Must be first. |
| `p` | see note below | `none`, `quarantine`, `reject` | Requested handling for messages that fail DMARC. Applies to the domain itself, and to subdomains unless `sp` or `np` overrides it. |
| `sp` | inherits `p` | `none`, `quarantine`, `reject` | Policy for **existing** subdomains that have no record of their own. |
| `np` | inherits `sp`, then `p` | `none`, `quarantine`, `reject` | Policy for **non-existent** subdomains (those that return `NXDOMAIN`). Ignored by receivers that predate RFC 9989. |
| `adkim` | `r` | `r` (relaxed), `s` (strict) | DKIM alignment mode. |
| `aspf` | `r` | `r` (relaxed), `s` (strict) | SPF alignment mode. |
| `t` | `n` | `y`, `n` | Test mode. `y` asks receivers to apply a softer policy while you trial a stricter one. |
| `psd` | `u` | `y`, `n`, `u` | Public suffix domain flag. Leave it out unless you operate a public suffix or need to declare an organizational-domain boundary in a delegated DNS tree. |
| `rua` | none | Comma-separated URIs | Where to send **aggregate** reports. Without it, no aggregate reports are generated. |
| `ruf` | none | Comma-separated URIs | Where to send **failure** (per-message) reports. Without it, no failure reports are generated. |
| `fo` | `0` | `0`, `1`, `d`, `s` | Which failures trigger failure reports. Ignored unless `ruf` is present. |

::callout{icon="i-heroicons-information-circle"}
**When `p` is missing:** a record without a valid `p` tag is treated as `p=none` if it contains at least one valid `rua` URI, so you still receive reports. Without a valid `rua`, receivers apply no DMARC processing at all. Always set `p` explicitly.
::

**Retired tags.** You may still see these in older records. Current receivers ignore them, and they should be removed at your next DNS change.

| Tag | What it did |
| --- | --- |
| `pct` | Applied the policy to a percentage (0 to 100, default 100) of failing messages, with the remainder handled one level softer. Receivers interpreted it inconsistently, which is why it was removed. Only receivers that still follow RFC 7489 honor it. |
| `rf` | Selected the failure report format. In practice only one format was ever used. |
| `ri` | Requested a report interval in seconds (default 86400). Most reporters ignored it and sent daily. |
| `!size` suffix | An obsolete size limit appended to a `rua` or `ruf` URI, for example `mailto:dmarc@example.com!10m`. Do not use it. |

#### DMARC policy values

| Value | Domain owner's request | Typical receiver behavior |
| --- | --- | --- |
| `none` | Monitoring only. No handling preference. | Delivers as normal. Aggregate reports still flow. Receivers must not change existing mail handling because of `p=none`. |
| `quarantine` | Treat failing mail as suspicious. It may still be legitimate. | Spam folder, junk marking or extra scrutiny. |
| `reject` | Failing mail is not a valid use of the domain. | Refuses the message during the SMTP session, in most cases with a `5xx` reply that mentions DMARC. |

Receivers make the final call. A receiver may deliver a message that fails a `reject` policy, for example because of a known mailing list, and may also treat a passing message with suspicion. Policy is a request, not a guarantee.

#### DMARC policy discovery and inheritance

When a message arrives, the receiver looks for a DMARC record at `_dmarc.<From domain>`. If none exists, it "walks" up the DNS tree one label at a time (at most eight queries) until it finds the record of the organizational domain.

The tag that governs a message depends on where the record was found:

| Situation | Record found at | Tag applied |
| --- | --- | --- |
| The `From:` domain publishes its own record | The domain itself | `p` |
| The `From:` domain is an existing subdomain with no record | The organizational domain | `sp`, otherwise `p` |
| The `From:` domain does not exist in DNS | The organizational domain | `np`, otherwise `sp`, otherwise `p` |

::callout{icon="i-heroicons-information-circle"}
**Inheritance differs from SPF.** DMARC policy can be inherited by subdomains that publish no record of their own. SPF is never inherited, so every sending subdomain needs its own SPF record. This is one reason each Postal sending domain should publish its own `_dmarc` record, with inheritance as a safety net.
::

#### DMARC identifier alignment

DMARC passes when at least one authenticated identifier is *aligned* with the `From:` domain:

| Mode | Tag value | Rule |
| --- | --- | --- |
| Relaxed | `r` | The two domains share the same organizational domain. Subdomains are allowed. |
| Strict | `s` | The two domains must be identical. |

| Authenticated domain | `From:` domain | Relaxed | Strict |
| --- | --- | --- | --- |
| `example.com` | `example.com` | Aligned | Aligned |
| `psrp.example.com` | `example.com` | Aligned | Not aligned |
| `mail.example.com` | `news.example.com` | Aligned | Not aligned |
| `example.net` | `example.com` | Not aligned | Not aligned |

Alignment applies to two different identifiers: `aspf` compares the SPF-authenticated envelope domain, and `adkim` compares the DKIM `d=` domain. They are independent settings, and Postal's recommended combination uses strict DKIM with relaxed SPF.

**Alignment in practice with Postal.** The table shows what DMARC sees for `From: hello@example.com` with `adkim=s; aspf=r`:

| Scenario | SPF-authenticated domain | DKIM `d=` | DMARC result |
| --- | --- | --- | --- |
| Domain fully configured | `psrp.example.com` (aligned, relaxed) | `example.com` (aligned) | **Pass** through SPF and DKIM |
| Return Path CNAME missing, so the envelope falls back to the global Return Path domain | `rp.postal.example.com` (not aligned) | `example.com` (aligned) | **Pass** through DKIM only |
| DKIM check not `OK`, so Postal signs with its fallback identity | `psrp.example.com` (aligned, relaxed) | `rp.postal.example.com` (not aligned) | **Pass** through SPF only. This is fragile and breaks when mail is forwarded. |
| Both missing | Not aligned | Not aligned | **Fail** |

The lesson: configure **both** the Return Path and DKIM, and confirm both in Postal's DNS checks before moving to enforcement.

#### DMARC aggregate reports (`rua`)

Aggregate reports are XML files (RFC 9990) that receivers send, normally once every 24 hours. They summarize the mail seen for your domain: sending IP addresses, message counts, SPF and DKIM results, alignment, and the disposition the receiver applied. They contain no message content.

- **Format and transport.** Reports arrive as compressed attachments by email. Reading them by hand is impractical, so route them to a mailbox that a DMARC analysis tool or your own parser can process.
- **Destination URIs.** A receiver that sends reports must support `mailto:`. Multiple destinations are separated by commas, for example `rua=mailto:dmarc@example.com,mailto:reports@example.org`. Commas and exclamation marks that are part of a URI must be percent-encoded.
- **External destinations.** If the reporting address belongs to a different organizational domain, the receiving domain must authorize it with a TXT record at `<your-domain>._report._dmarc.<reporting-domain>`. Without this record, receivers ignore that destination.

```dns
example.com._report._dmarc.reports.example.net.    TXT    "v=DMARC1"
```

A wildcard such as `*._report._dmarc.reports.example.net` can authorize reports for every domain, which is convenient for report-processing services.

#### DMARC failure reports (`ruf` and `fo`)

Failure reports are per-message copies of individual failures, described in RFC 9991. They can help debug a specific problem, but they contain message details. Many large receivers therefore send them heavily redacted, or not at all. Treat them as a bonus, not a dependency, and never rely on them for monitoring.

The `fo` tag selects which failures are reported. Combine values with colons, for example `fo=1:d:s`. The values `0` and `1` are mutually exclusive.

| `fo` value | Report generated when |
| --- | --- |
| `0` (default) | **All** underlying mechanisms fail to produce an aligned pass. |
| `1` | **Any** underlying mechanism fails to produce an aligned pass. |
| `d` | A DKIM signature fails evaluation, whether or not it is aligned. |
| `s` | SPF evaluation fails, whether or not it is aligned. |

#### DMARC test mode and rollout

The `t` tag replaces the old percentage-based rollout with a simple switch:

| Configured policy | With `t=y`, a failing message is handled as |
| --- | --- |
| `p=reject` | `quarantine` |
| `p=quarantine` | `none` |
| `p=none` | Unchanged. `t` has no effect on `none`. |

`t=y` never affects report generation, so you keep full visibility while testing.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
A receiver that has not yet implemented RFC 9989 ignores `t` as an unknown tag and enforces `p` exactly as written. If a rejected message would be costly, step through `p=quarantine` first rather than relying on `p=reject; t=y` alone.
::

A dependable rollout path:

| Stage | Record | Goal |
| --- | --- | --- |
| 1. Monitor | `p=none; rua=mailto:...` | Discover every sender. Run long enough to cover all mail cycles, including monthly and quarterly mailings. |
| 2. Fix | Unchanged | Bring every legitimate sender into SPF or DKIM alignment. |
| 3. Soft enforce | `p=quarantine` | Confirm that legitimate mail is unaffected. |
| 4. Trial reject | `p=reject; t=y` (optional) | Practice rejection with a safety net. |
| 5. Enforce | `p=reject` | Final hardened state. |

#### DMARC record variants

**Monitoring only:**

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=none; rua=mailto:dmarc@example.com"
```

**Hardened production policy (Postal recommendation):**

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; rua=mailto:dmarc@example.com"
```

**Everything strict.** Use only if every sender uses the exact domain for both SPF and DKIM. This does not fit Postal's Return Path subdomain design:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; adkim=s; aspf=s; rua=mailto:dmarc@example.com"
```

**Different policy for subdomains.** Enforce on the parent while keeping subdomains softer during a rollout:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=quarantine; rua=mailto:dmarc@example.com"
```

**Protect names that do not exist** (spoofers often invent subdomains such as `invoice.example.com`):

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; np=reject; rua=mailto:dmarc@example.com"
```

**Aggregate and failure reports to different mailboxes:**

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=quarantine; rua=mailto:dmarc@example.com; ruf=mailto:forensic@example.com; fo=1"
```

**Reports sent to a third-party service** (requires the authorization record described above):

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; rua=mailto:example-com@reports.example.net"
```

#### DMARC and indirect mail flows

Mailing lists, alumni forwarders and role-based aliases relay messages. Relaying changes the sending IP, so SPF fails, and list software often rewrites the subject or body, so DKIM can fail as well. A domain with `p=reject` can therefore see legitimate relayed mail refused. RFC 7960 documents these interoperability limits.

Two practical rules follow:

- A domain that publishes `p=reject` **must not rely on SPF alone**. It must apply valid DKIM signatures, which normally survive forwarding.
- Domains whose users take part in mailing lists should weigh `p=quarantine` against `p=reject`. Transactional domains, which send machine-generated mail, are generally safe to reject.

::callout{icon="i-heroicons-information-circle"}
Large mailbox providers already expect bulk senders to authenticate with SPF and DKIM and to publish a DMARC policy. A well-formed record is increasingly a delivery prerequisite, not just a security option.
::

#### DMARC troubleshooting

| Symptom | Likely cause |
| --- | --- |
| The policy is not applied | More than one DMARC record at `_dmarc`, `v=DMARC1` is not first, or the record contains smart quotes or a missing semicolon. |
| SPF passes but DMARC fails | The SPF-authenticated domain is not aligned. Check the Return Path CNAME, and remember `aspf=s` rejects subdomains. |
| DKIM passes but DMARC fails | The `d=` domain differs from the `From:` domain, often because Postal fell back to its own signing identity, or `adkim=s` is meeting a subdomain. |
| No reports arrive | A typo in `rua`, an unauthorized external destination, or too little time: reports arrive daily, and some receivers send none. |
| A subdomain's mail is rejected unexpectedly | The subdomain has no record and inherits `sp` (or `p`) from the parent. |

### Return Path and bounce handling reference

The Return Path is the envelope sender (`MAIL FROM`) of a message. It is where delivery failure notices are sent, and it is the identity SPF authenticates. Postal exposes it as a per-domain hostname built from `dns.custom_return_path_prefix`.

#### Why a custom Return Path matters

| Design | Envelope sender | SPF alignment with `From: example.com` |
| --- | --- | --- |
| Global Return Path only | `…@rp.postal.example.com` | Not aligned (different organizational domain). |
| Per-domain Return Path (`psrp`) | `…@psrp.example.com` | Aligned under `aspf=r`. |

The per-domain CNAME points the sending domain's Return Path at Postal's Return Path host. Bounces are delivered to Postal, and SPF passes on a domain that shares the visible sender's organizational domain.

#### Per-message envelope addresses

Sending platforms commonly give every message a unique envelope address, a technique known as **VERP** (Variable Envelope Return Path). When a bounce arrives at that address, the platform can tie it to the exact message and recipient without parsing the bounce body.

#### SMTP reply classes and enhanced status codes

A remote server's reply decides whether a message is retried or bounced. The first digit gives the class, and an enhanced code such as `5.1.1` (RFC 3463) adds detail.

| Class | Meaning | Outcome |
| --- | --- | --- |
| `2.x.x` | Success | Message accepted. |
| `4.x.x` | Persistent transient failure | The sender retries later. |
| `5.x.x` | Permanent failure | The sender stops and generates a bounce (a delivery status notification, RFC 3464). |

| Code | Typical meaning |
| --- | --- |
| `5.1.1` | The recipient mailbox does not exist. |
| `4.2.2` | The recipient mailbox is full. |
| `5.7.1` | Rejected by policy, often for authentication or reputation reasons. |

::callout{icon="i-heroicons-information-circle"}
The delivery status notification is sent to the envelope sender, and it is sent with an **empty** `MAIL FROM:<>` of its own so bounces can never trigger further bounces.
::

### MX reference

MX (Mail Exchanger) records tell the world which servers accept mail for a domain.

```dns
example.com.    MX    10 postal.example.com.
```

The number is the **preference**, and **lower values are tried first**. The target must be a hostname that has an `A` or `AAAA` record. It must not be an IP address and must not be a CNAME.

| Setup | Records | Effect |
| --- | --- | --- |
| Single server | `10 postal.example.com.` | All inbound mail goes to one host. |
| Load sharing | `10 mx1.example.com.` and `10 mx2.example.com.` | Equal preference: senders spread the load. |
| Primary and backup | `10 mx1.example.com.` and `20 mx2.example.com.` | The backup is used only if the primary is unreachable. |
| No inbound mail (null MX) | `0 .` | Declares that the domain accepts no mail (RFC 7505). |
| No MX at all | (none) | Senders fall back to the domain's own `A`/`AAAA` record (an "implicit MX"). |

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
A backup MX that accepts mail without validating recipients turns your domain into a backscatter source and a spam target. Keep every MX host equally strict about recipient checks, or run a single well-provisioned MX.
::

### Reverse DNS and FCrDNS reference

The HELO/EHLO hostname should be a real public FQDN that is consistent with the public IP address used for outbound SMTP connections. Three related DNS concepts define "consistent":

- **Forward DNS:** the hostname resolves to the sending IP address through an `A` and/or `AAAA` record.
- **Reverse DNS (rDNS/PTR):** the sending IP address has a `PTR` record that returns the SMTP hostname.
- **FCrDNS (Forward-Confirmed Reverse DNS):** the hostname returned by the `PTR` record resolves forward to the same IP address.

For IPv4:

```text
203.0.113.10
    PTR → postal.example.com

postal.example.com
    A → 203.0.113.10
```

With IPv6, the same consistency must exist for the address used for SMTP connections:

```text
2001:db8::10
    PTR → postal.example.com

postal.example.com
    AAAA → 2001:db8::10
```

The resulting identity chain is:

```text
Outbound SMTP IP
       │
       ▼
    PTR/rDNS
       │
       ▼
HELO/EHLO hostname
       │
       ▼
   A / AAAA
       │
       ▼
same SMTP IP
```

This is the practical meaning of FCrDNS: the reverse and forward mappings confirm each other. FCrDNS is not a separate DNS record and has no Postal-specific switch.

#### Reverse DNS details

- **Who controls PTR.** A PTR record lives in the reverse zone of the IP block (`in-addr.arpa` for IPv4 and `ip6.arpa` for IPv6), which belongs to whoever owns the address range, usually your hosting provider or ISP. You normally set it in the provider's control panel, not in your own DNS zone.
- **One PTR per IP.** Publish a single PTR record for each sending IP. Several PTR records make the result ambiguous.
- **Several outbound IPs.** Every sending IP needs its own PTR, and the name it returns must resolve forward to that IP.
- **Avoid generic provider names.** A PTR such as `static-203-0-113-10.provider.example` marks the address as dynamic or residential to many receivers, and is often penalized. Use your own domain.
- **IPv4 and IPv6 are separate.** If Postal can connect over IPv6, that address needs its own PTR and `AAAA` record. Missing IPv6 reverse DNS is a frequent cause of rejection.

#### SPF for the HELO identity

Because SPF also evaluates the HELO/EHLO name (and relies on it when the envelope sender is empty), it is good practice to publish a small SPF record for the HELO hostname itself, provided its `A`/`AAAA` records hold your outbound IP addresses:

```dns
postal.example.com.    TXT    "v=spf1 a -all"
```

#### Additional verification

Confirm the certificate a remote system sees on the SMTP port, using the hostname you announce:

```bash
openssl s_client -starttls smtp -connect postal.example.com:25 -servername postal.example.com
```

The certificate should list the HELO/EHLO hostname and chain to a trusted authority.

### Optional transport security and brand layers

The records in Part 1 provide the authentication a Postal sending domain needs. The mechanisms below are optional. They depend on whether the domain also receives mail, and on whether you want transport enforcement, TLS visibility or brand display.

| Mechanism | What it does | Published at | Protects | Needs | Configured in Postal? |
| --- | --- | --- | --- | --- | --- |
| [MTA-STS](#mta-sts-for-inbound-mail) | Tells senders to require TLS and to verify your MX hostnames | `_mta-sts.<domain>` (TXT) plus an HTTPS policy file | Mail **to** your domain | HTTPS certificate on the policy host, and STARTTLS with a valid certificate on each MX | No |
| [TLS-RPT](#smtp-tls-reporting-tls-rpt) | Sends you reports about TLS delivery failures | `_smtp._tls.<domain>` (TXT) | Visibility for mail **to** your domain | A mailbox or HTTPS endpoint | No |
| [DANE](#dane-for-smtp) | Pins the MX certificate or key in DNSSEC-signed DNS | `_25._tcp.<mx-host>` (TLSA) | Mail **to** your domain | DNSSEC | No |
| [BIMI](#bimi) | Displays a verified brand logo in supporting inboxes | `default._bimi.<domain>` (TXT) | Brand recognition for mail **from** your domain | DMARC enforcement, an SVG logo and usually a mark certificate | No |

### MTA-STS for inbound mail

MTA-STS (RFC 8461) protects **inbound** SMTP delivery to a domain. It lets sending servers require TLS and verify that the MX hostname they connect to is one the domain has authorized. It is relevant only when the domain actually receives mail.

For example, if:

```text
example.com. MX 10 postal.example.com.
```

the policy can be published at:

```text
https://mta-sts.example.com/.well-known/mta-sts.txt
```

with the following contents:

```text
version: STSv1
mode: enforce
mx: postal.example.com
max_age: 604800
```

The policy host needs a valid HTTPS certificate, and the `mx:` entries must match the TLS-capable MX hosts the domain uses. The receiving SMTP service must support STARTTLS before an MTA-STS policy is enforced. The policy file is retrieved over HTTPS from the `mta-sts` host and is not stored in DNS.

A separate discovery record is published at `_mta-sts.example.com`:

```dns
_mta-sts.example.com.    TXT    "v=STSv1; id=2026091801"
```

#### MTA-STS discovery record

| Tag | Required | Meaning |
| --- | --- | --- |
| `v` | Yes | Must be `STSv1`, and must come first. |
| `id` | Yes | An opaque policy version identifier of 1 to 32 letters and digits. Change it **whenever the policy changes**, so supporting senders refresh their cached copy. A date-based value such as `2026091801` works well. |

#### MTA-STS policy fields

| Field | Required | Values | Meaning |
| --- | --- | --- | --- |
| `version` | Yes | `STSv1` | Policy version. |
| `mode` | Yes | `enforce`, `testing`, `none` | How senders must behave. See the modes below. |
| `mx` | Yes when `mode` is `testing` or `enforce` | A hostname, or a wildcard such as `*.example.com` | Permitted MX hostnames. Repeat the field once per host. A wildcard matches exactly one left-most label, so `*.example.com` covers `mx1.example.com` but neither `example.com` nor `a.b.example.com`. |
| `max_age` | Yes | Seconds, up to 31557600 (about one year) | How long senders may cache the policy. |

For several MX hosts:

```text
version: STSv1
mode: enforce
mx: mx1.example.com
mx: mx2.example.com
max_age: 604800
```

#### MTA-STS modes

| Mode | Sender behavior | Use it when |
| --- | --- | --- |
| `testing` | Attempts delivery even if TLS validation fails, and reports the failure through TLS-RPT. | You are validating policy coverage and TLS behavior. |
| `enforce` | Delivers only over TLS with a valid certificate that matches an allowed MX host. Otherwise delivery is deferred. | All MX hosts are ready. |
| `none` | Behaves as if no policy exists. | You are withdrawing MTA-STS, or the domain has a null MX. |

When `mode` is `testing` or `enforce`, the policy must contain at least one `mx:` entry.

#### MTA-STS policy hosting requirements

- The file is served over **HTTPS** at `https://mta-sts.<domain>/.well-known/mta-sts.txt`, and the host `mta-sts.<domain>` needs a certificate that browsers would trust.
- Serve it as `text/plain`.
- HTTP redirects are **not followed**. Serve the file directly from the `mta-sts` host.
- Each MX host must present a valid, trusted certificate that matches its hostname.
- Senders require TLS 1.2 or later.

#### Deploying MTA-STS safely

1. Confirm every MX host offers STARTTLS with a valid certificate.
2. Publish the policy with `mode: testing`, a modest `max_age`, and a TLS-RPT record.
3. Watch TLS-RPT reports until the failures stop.
4. Switch to `mode: enforce` and raise `max_age` to weeks or more, then update `id`.
5. To withdraw MTA-STS, publish `mode: none` with a fresh `id`, and keep it in place until the previous `max_age` has elapsed before removing the records.

::callout{icon="i-heroicons-information-circle"}
For a single-node Postal deployment, `postal.example.com` may be the only MX listed in both DNS and the MTA-STS policy. For a multi-node deployment, list each permitted MX hostname separately. MTA-STS does not configure Postal; it is a domain-level receiving policy.
::

### SMTP TLS Reporting (TLS-RPT)

SMTP TLS Reporting (TLS-RPT, RFC 8460) is a **reporting mechanism**, not a TLS enforcement policy. It tells sending mail systems where to submit aggregate reports about TLS problems they encountered when connecting to a receiving domain. It is most useful alongside MTA-STS or DANE, which provide the actual transport-security policy.

TLS-RPT is configured in DNS for the **receiving domain**. It is not a `postal.yml` setting, and it does not control how Postal sends mail to unrelated recipient domains.

For `example.com`, publish exactly one effective TLS-RPT policy at:

```dns
_smtp._tls.example.com.    TXT    "v=TLSRPTv1; rua=mailto:tlsrpt@example.com"
```

The format is deliberately small. TLS-RPT v1 defines two policy fields:

| Field | Required | Description |
| --- | --- | --- |
| `v` | **Yes** | Must be exactly `TLSRPTv1` and appear first in the record. |
| `rua` | **Yes** | One or more report destination URIs. `mailto:` and `https:` are the supported schemes. |

A policy may list more than one destination:

```dns
_smtp._tls.example.com.    TXT    "v=TLSRPTv1; rua=mailto:tlsrpt@example.com, https://reports.example.com/tls"
```

Whitespace around semicolons and commas is allowed. URI delimiters that belong to a URI, such as commas, exclamation marks and semicolons, must be percent-encoded rather than interpreted as TLS-RPT syntax.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
**Publish one effective TLS-RPT policy.** If DNS returns several `v=TLSRPTv1` records for `_smtp._tls.<domain>`, senders must treat the domain as not implementing TLS-RPT. Records that do not begin with `v=TLSRPTv1;` are ignored when determining the effective set.
::

#### TLS-RPT DNS record details

A DNS provider may split a single TXT record into several quoted character strings, for example:

```dns
_smtp._tls.example.com. TXT (
    "v=TLSRPTv1; "
    "rua=mailto:tlsrpt@example.com"
)
```

The strings are joined **without an inserted space** before TLS-RPT parsing, so keep separators exactly where the format requires them.

TLS-RPT v1 parsers must accept syntactically valid extension fields. Implementations that support a compatible superset of the specification ignore unknown extension fields. Do not rely on private fields for interoperability.

Unlike DMARC, TLS-RPT does **not** define a separate DNS authorization record for third-party reporting destinations. The `rua` URI can point to another domain, and the report receiver is responsible for protecting and operating that endpoint correctly.

::callout{icon="i-heroicons-information-circle"}
For security and operational reliability, use an HTTPS endpoint with a valid certificate or a dedicated mailbox that can accept automated aggregate reports. Avoid routing TLS-RPT reports into the same infrastructure whose TLS failures you are trying to diagnose.
::

#### TLS-RPT report transports

**Email (`mailto:`).** When `rua` contains a `mailto:` URI, the report is delivered as an email message. The machine-readable report uses `multipart/report` with `report-type="tlsrpt"`. Its data part is `application/tlsrpt+json`, or `application/tlsrpt+gzip` when compressed.

TLS-RPT email reports use these headers:

```text
TLS-Report-Domain: example.com
TLS-Report-Submitter: sender.example.net
```

The report body is I-JSON. Gzip compression is recommended because aggregate reports can become large.

**HTTPS (`https:`).** When `rua` contains an `https:` URI, the report is submitted to that endpoint with an HTTP `POST`. The endpoint should accept the TLS-RPT media type and return a successful HTTP response once the report has been accepted.

A sender may support several `rua` destinations and may try another one if the first is unavailable. Delivery is complete only when at least one configured destination has accepted the report.

#### TLS-RPT report format

TLS-RPT reports are aggregate JSON documents. A report looks like this:

```json
{
  "organization-name": "Example Organization",
  "date-range": {
    "start-datetime": "2026-09-18T00:00:00Z",
    "end-datetime": "2026-09-19T00:00:00Z"
  },
  "contact-info": "mailto:tlsrpt@example.com",
  "report-id": "example-20260918-001",
  "policies": [
    {
      "policy": {
        "policy-type": "sts",
        "policy-string": "version: STSv1; mode: enforce; mx: postal.example.com",
        "policy-domain": "example.com",
        "mx-host": "postal.example.com"
      },
      "summary": {
        "total-successful-session-count": 1200,
        "total-failure-session-count": 3
      },
      "failure-details": []
    }
  ]
}
```

The main fields are:

| Field | Description |
| --- | --- |
| `organization-name` | Organization responsible for the report. |
| `date-range` | UTC start and end timestamps covered by the report. |
| `contact-info` | Contact information for the report submitter. |
| `report-id` | Unique report identifier. |
| `policies` | Array of policy observations and their session counts. |
| `policy.policy-type` | `sts`, `tlsa`, or `no-policy-found`. |
| `policy.policy-string` | The applicable MTA-STS policy or DANE TLSA data, or the literal `no-policy-found`. |
| `policy.policy-domain` | Domain for which the policy was evaluated. |
| `policy.mx-host` | MX hostname or policy MX pattern involved. |
| `summary.total-successful-session-count` | Number of successful TLS sessions. |
| `summary.total-failure-session-count` | Number of failed TLS sessions. |
| `failure-details` | Array describing the observed failure categories. |

A failure detail can include `result-type`, `sending-mta-ip`, `receiving-mx-hostname`, `receiving-mx-helo`, `receiving-ip`, `failed-session-count`, `additional-information` and `failure-reason-code`.

The standardized result categories are:

| Result type | Meaning |
| --- | --- |
| `starttls-not-supported` | The receiving SMTP server did not offer STARTTLS. |
| `certificate-host-mismatch` | The presented certificate did not match the expected SMTP hostname. |
| `certificate-expired` | The certificate was expired. |
| `certificate-not-trusted` | The certificate could not be validated against the expected trust model. |
| `validation-failure` | A TLS validation failure that does not fit another defined category. |
| `tlsa-invalid` | The DANE TLSA data could not be used successfully. |
| `dnssec-invalid` | DNSSEC validation failed. |
| `dane-required` | DANE was required but could not be successfully used. |
| `sts-policy-fetch-error` | The MTA-STS policy could not be retrieved. |
| `sts-policy-invalid` | The retrieved MTA-STS policy was invalid. |
| `sts-webpki-invalid` | The HTTPS MTA-STS policy could not be authenticated with normal Web PKI validation. |

A single failed session may appear under more than one failure detail when several independent checks fail. Transient failures, such as a busy network or a TCP timeout, are not required to be reported.

#### TLS-RPT reporting interval, compression, and retries

Reports normally cover a daily UTC reporting period. The reporting implementation may delay submission to avoid synchronized bursts of traffic.

Gzip compression is recommended for both email and HTTPS delivery. The media types are:

```text
application/tlsrpt+gzip     (compressed)
application/tlsrpt+json     (uncompressed)
```

A failed report delivery should be retried for up to 24 hours with an appropriate backoff strategy. Reporting systems should tolerate delayed or duplicated reports by treating the report ID as a stable identifier.

#### TLS-RPT and MTA-STS/DANE

TLS-RPT does not enforce encrypted SMTP on its own.

```text
TLS-RPT
    = reporting

MTA-STS
    = policy and certificate/hostname enforcement through HTTPS policy

DANE
    = DNSSEC-backed TLSA policy
```

For a domain protected by MTA-STS or DANE, TLS-RPT provides visibility into the policy and TLS failures that sending MTAs encounter.

::callout{icon="i-heroicons-information-circle"}
Publishing `_smtp._tls.example.com` affects MTAs delivering **to** `example.com`. It does not create a global TLS policy for mail sent by Postal. When Postal delivers to a recipient domain, Postal is the sender and the recipient domain's TLS policies apply.
::

When TLS-RPT reports are themselves delivered by SMTP, an implementation must not let an MTA-STS or DANE TLSA failure for the report's own delivery stop the reporting mechanism from working. This exception exists so that transport-security failures can still be reported.

#### TLS-RPT operational checklist

```text
[ ] Publish exactly one effective _smtp._tls TXT record.
[ ] Use v=TLSRPTv1 as the first field.
[ ] Configure at least one valid mailto: or https: rua destination.
[ ] Make sure the report destination can accept aggregate reports.
[ ] Prefer gzip compression for large reports.
[ ] Monitor failure categories instead of treating any single transient failure as proof of an outage.
[ ] Use TLS-RPT together with MTA-STS or DANE when transport enforcement is required.
[ ] Keep the reporting endpoint independent from the SMTP service being monitored.
```

### DANE for SMTP

DANE (RFC 6698, with SMTP-specific rules in RFC 7672) provides certificate pinning and TLS enforcement for **inbound** SMTP, and it requires DNSSEC. It is an advanced option that demands careful certificate and key rotation, because the TLSA record must stay synchronized with the SMTP service's certificate or public key.

For an SMTP service at `postal.example.com` on TCP port 25, publish a TLSA record at:

```dns
_25._tcp.postal.example.com.    TLSA    3 1 1 <SHA256_SPKI_DIGEST>
```

The record has three numeric parameters followed by the certificate association data.

#### TLSA parameters

| Field | Value | Name | Meaning for SMTP |
| --- | --- | --- | --- |
| **Usage** | `0` | PKIX-TA | Not used with SMTP. |
| | `1` | PKIX-EE | Not used with SMTP. |
| | `2` | DANE-TA | Supported. Pins a trust anchor (CA) that must appear in the server's certificate chain. The hostname in the certificate is checked. |
| | `3` | DANE-EE | Supported and most common. Pins the server's own certificate or key. The certificate name and expiry are not checked by DANE clients. |
| **Selector** | `0` | Full certificate | The data covers the whole certificate, so it changes at every renewal. |
| | `1` | Public key (SPKI) | The data covers the public key only, so it survives renewals that reuse the same key. |
| **Matching type** | `0` | Exact match | The data is the full certificate or key. |
| | `1` | SHA-256 | The data is a SHA-256 digest. |
| | `2` | SHA-512 | The data is a SHA-512 digest. |

The most common and easiest-to-maintain combinations are `3 1 1` and `2 1 1`. The example above uses usage `3` (DANE-EE), selector `1` (SPKI) and matching type `1` (SHA-256).

Generate the digest from the public key material used by the SMTP certificate. Never copy the placeholder:

```bash
openssl x509 -in fullchain.pem -noout -pubkey \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -binary \
  | xxd -p -c 64
```

#### DANE requirements

Never enable DANE by adding a TLSA record alone. All of the following must hold:

- The zone carrying the MX records, and the zone carrying the MX host's address records, are **DNSSEC-signed** and validate.
- The TLSA record sits at `_25._tcp.<mx-hostname>`, that is, at the **MX host** and not at the mail domain.
- The SMTP service offers STARTTLS with a certificate that matches the TLSA record.
- Your MX hosts are stable enough to meet the operational demands of DANE.

Once a validated TLSA record exists, DANE-aware senders will not fall back to unauthenticated or plaintext delivery, so a mismatch causes deferred mail.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
A stale TLSA record can make mail delivery fail. Treat certificate renewal, key rotation, DNSSEC maintenance and TLSA updates as one change set.
::

#### DANE key rotation

1. Publish the TLSA record for the **new** key next to the existing one, so two records are live.
2. Wait until the old record's TTL has expired everywhere.
3. Install the new certificate.
4. Remove the old TLSA record after the change has settled.

If you renew certificates with the **same key** and use selector `1`, the TLSA record never changes. Many ACME clients can reuse the key on renewal (for Certbot, `--reuse-key`).

### BIMI

BIMI (Brand Indicators for Message Identification) is an optional branding mechanism for participating mailbox providers. It does not improve Postal's SMTP delivery logic and is not configured in `postal.yml`.

A typical record uses the `default` selector:

```dns
default._bimi.example.com.    TXT    "v=BIMI1; l=https://example.com/logo.svg; a=https://example.com/bimi_cert.pem"
```

#### BIMI record tags

| Tag | Required | Meaning |
| --- | --- | --- |
| `v` | Yes | Must be `BIMI1`, and must come first. |
| `l` | Yes | HTTPS URL of the SVG logo. An empty `l=` (with an empty `a=`) declares that the domain chooses not to participate. |
| `a` | Optional in the specification, required by some providers | HTTPS URL of the evidence document, a PEM file containing the mark certificate. |
| `avp` | No | Avatar preference: `brand` (default) or `personal`. This tells providers whether to show the brand logo or the sender's personal avatar. Support is not universal. |

To use a selector other than `default`, add a `BIMI-Selector` header to the message (and sign it with DKIM):

```text
BIMI-Selector: v=BIMI1; s=marketing
```

The record is then read from `marketing._bimi.example.com`.

#### BIMI requirements

| Requirement | Detail |
| --- | --- |
| **DMARC enforcement** | The domain's policy must be `p=quarantine` or `p=reject`. `p=none` does not qualify. A `pct` tag below 100, if you still publish one, blocks display. If you publish `sp`, it should not be `none`. |
| **Authentication** | SPF and DKIM must pass and align with the `From:` domain. |
| **Logo** | SVG Tiny Portable/Secure profile, square, hosted over HTTPS and kept small (commonly under 32 KB). |
| **Certificate** | A Verified Mark Certificate (VMC) proves a registered trademark and enables the verified checkmark in Gmail. A Common Mark Certificate (CMC) needs no trademark and shows the logo without the checkmark. Requirements differ by provider. |

::callout{icon="i-heroicons-information-circle"}
Postal does not generate or validate BIMI records. Treat BIMI as optional DNS and brand configuration on the sending domain. BIMI is specified by the AuthIndicators Working Group and provider requirements evolve, so check each mailbox provider's current documentation before you invest in a certificate.
::

### Hardening unused domains and subdomains

A domain that never sends mail should still be protected against spoofing. Attackers favor forgotten domains precisely because nobody watches them.

For a domain with **no legitimate outbound mail**, publish:

```dns
example.net.    TXT    "v=spf1 -all"
_dmarc.example.net.    TXT    "v=DMARC1; p=reject; sp=reject"
```

Add `rua=mailto:dmarc@example.net` to the DMARC record if you want aggregate reports that reveal spoofing attempts.

If the domain also does not accept inbound mail, publish a null MX:

```dns
example.net.    MX    0 .
```

A null MX is better than leaving MX records out, because SMTP senders otherwise fall back to the domain's `A`/`AAAA` record.

If you also publish an MTA-STS policy for a domain with a null MX, use `mode: none` and list no `mx:` entries. An enforcing or testing policy without an MX service contradicts the domain's intent.

If old DKIM selectors exist for the unused domain, remove them or publish revoked keys. For broad subdomain hardening, a wildcard revoked key can be used where appropriate:

```dns
*._domainkey.example.net.    TXT    "v=DKIM1; p=;"
```

SPF does not inherit from a parent to its subdomains, so cover unused subdomains with a wildcard as well. It applies to subdomains that have no DNS records of their own:

```dns
*.example.net.    TXT    "v=spf1 -all"
```

The baseline for a non-sending domain:

| Control | Record | Purpose |
| --- | --- | --- |
| SPF | `example.net TXT "v=spf1 -all"` | No server may send mail as this domain. |
| DMARC | `_dmarc.example.net TXT "v=DMARC1; p=reject; sp=reject"` | Receivers reject spoofed mail. |
| Null MX | `example.net MX 0 .` | The domain accepts no mail. |
| DKIM | `*._domainkey.example.net TXT "v=DKIM1; p=;"` | Any key for the domain is revoked. |

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
Never apply this configuration to a domain that Postal or any other service uses for legitimate mail. `v=spf1 -all` is a hard fail meant for domains with no legitimate senders. Review every sending subdomain before adding wildcard hardening, because a wildcard also covers subdomains you may have forgotten, and DMARC policy set on the parent can be inherited by any subdomain without its own record.
::
