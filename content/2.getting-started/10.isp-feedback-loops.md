# ISP feedback loops

Feedback loops (FBLs) help senders detect when recipients report messages as spam or junk. A traditional FBL usually returns an **Abuse Reporting Format (ARF)** complaint report; newer programs may instead expose campaign-level complaint data or sender-reputation metrics through a postmaster dashboard.

FBLs are useful for suppression, list hygiene, abuse detection, and deliverability diagnostics, but they are not standardized across mailbox providers. Programs differ in eligibility, authentication, report format, privacy filtering, enrollment, and retention. Some providers do not publish a conventional FBL at all.

> **Provider data changes.** Treat the links below as entry points to the provider's current documentation, not as permanent API contracts. Verify eligibility, enrollment, report contents, and authentication requirements before automating against a program.

## Traditional FBLs and ARF

A traditional FBL is typically a provider-generated complaint report sent back to an enrolled sender when a recipient marks a message as spam or junk.

The common report format is **Abuse Reporting Format (ARF)**, normally carried as a MIME report with structured complaint metadata and message-header information. Exact contents vary by provider. A report may contain enough information to identify the sender and original message, but providers can redact recipient addresses or other fields for privacy.

For operational processing, do not assume that every FBL contains a complete copy of the original message or an actionable recipient address. Build your parser around the fields the specific provider documents and keep the provider source separate from your normalization logic.

## Gmail Feedback Loop

Gmail uses a different model from traditional ISP complaint programs. Eligible senders can use Gmail's **Feedback Loop (FBL)** to identify campaigns that generate spam complaints from **personal Gmail accounts**. Reporting is aggregate and appears in Google Postmaster Tools rather than as a conventional stream of individual complaint emails.

Gmail associates campaign complaint data with a `Feedback-ID` message header.

### `Feedback-ID` format

```text
Feedback-ID: a:b:c:SenderId
```

The first three fields are optional identifiers. They can represent a campaign, customer, message type, tenant, or another aggregation dimension. The final `SenderId` is mandatory, must be **5–15 characters**, and should remain consistent for the mail stream it represents.

Example:

```text
Feedback-ID: onboarding:customer42:transactional:sender01
```

Choose identifiers that produce useful aggregates. Creating a unique identifier for every message fragments traffic and may leave individual identifiers below the reporting threshold.

### Gmail implementation requirements

1. Add exactly **one** `Feedback-ID` header to the message.
2. Use stable identifiers for the campaign, customer, or traffic class you actually want to analyze.
3. Add the header **before the final DKIM signature is created**.
4. DKIM-sign the delivered message with a domain you own or control, after the `Feedback-ID` header has been added.
5. Add and verify that signing domain in Google Postmaster Tools.
6. Publish the sending IPs in the SPF records of the signing domain and maintain valid PTR/reverse-DNS records for the sending IPs.
7. Continue to process unsubscribes, bounces, and suppression events through the normal mail pipeline; Gmail FBL data is a diagnostic campaign signal, not a replacement for suppression handling.

Gmail requires the traffic to be DKIM-signed after the `Feedback-ID` header is added so the identifier cannot simply be spoofed. Gmail may also omit or suppress low-volume identifiers when there are too few messages or too few distinct spam reports to populate the dashboard.

### Gmail data limits and interpretation

Gmail's FBL is not a recipient-level complaint export. Treat the dashboard as an aggregate campaign signal.

A missing feedback-loop identifier does **not** prove that zero recipients complained. Reporting can be absent when traffic or complaint volume is below the threshold needed for the dashboard to display the identifier, and Postmaster Tools may omit some data on low-volume days for privacy reasons.

## Postal implementation notes

Postal supports custom message construction through SMTP and API workflows and signs outbound mail with DKIM. Its current documentation lists the standard headers included in Postal's generated DKIM signature; `Feedback-ID` is not part of that documented default header list.

For Gmail FBL, the important verification target is therefore the **final message received by Gmail**, not the message as it looked when it entered Postal.

A safe workflow is:

1. Insert `Feedback-ID` into the outbound message.
2. Ensure the final sender-controlled DKIM signer covers the header after insertion.
3. Deliver a test message to a Gmail mailbox.
4. Inspect the raw delivered message and confirm that `Feedback-ID` is present.
5. Confirm that the DKIM `h=` signed-header list includes `Feedback-ID`.
6. Re-check this after any gateway, relay, mailing-list, or post-processing layer that can add or rewrite headers.

Do not infer that a header is DKIM-signed simply because Postal accepted and transported it. Verify the delivered signature.

## Working with complaint data

An FBL should feed an operational workflow, not just a dashboard.

When a complaint arrives:

1. Parse and validate the report according to the provider's format.
2. Correlate the complaint with the sending source using stable identifiers such as `Message-ID`, DKIM domain/selector, envelope sender, recipient domain, and campaign metadata where available.
3. Suppress the complaining recipient when the provider exposes an actionable recipient identifier and the complaint is relevant to the mail stream being managed.
4. Preserve the report and correlation metadata long enough to diagnose abuse, acquisition, targeting, frequency, or content problems.
5. Investigate the upstream cause rather than treating the complaint as an isolated event.

Common root causes include:

* unclear or weak subscription consent,
* stale or low-quality lists,
* purchased or rented addresses,
* excessive send frequency,
* misleading subject lines or content,
* difficult unsubscribe flows,
* accidental cross-mailing between tenants or customer segments, and
* compromised accounts or sending infrastructure.

## Authentication and sender hygiene

FBL data is much easier to use when sender identity is stable. At minimum, bulk senders should maintain:

* **SPF** for authorized sending infrastructure,
* **DKIM** for message authentication and domain attribution,
* **DMARC** for alignment and spoofing protection,
* valid forward and reverse DNS for sending IPs,
* stable envelope and header identities that can be correlated in telemetry, and
* clear suppression handling for complaints, bounces, and unsubscribe requests.

Keep transactional and promotional traffic logically separated when practical. A complaint spike from one traffic class should be diagnosable without obscuring the behavior of another stream.

## FBL versus postmaster tools

These terms are often mixed together, but they serve different purposes:

| Tool type                       | Typical output                                                     | Common use                                          |
| ------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------- |
| **Traditional FBL**             | Individual or semi-individual complaint reports, often ARF         | Suppression, abuse detection, complaint correlation |
| **Campaign FBL**                | Aggregate complaint metrics keyed by campaign ID                   | Campaign diagnostics and complaint-rate analysis    |
| **Postmaster dashboard**        | Reputation, authentication, spam-rate, delivery, or volume metrics | Deliverability monitoring and troubleshooting       |
| **Blocklist / delist workflow** | IP/domain status and remediation path                              | Delivery failure investigation                      |

A provider may offer one, several, or none of these mechanisms. Do not infer that the absence of a public FBL means the provider exposes no complaint signal internally, or that a postmaster dashboard is a substitute for an FBL.

## Operational cautions

An FBL rarely represents every complaint made by every recipient. Coverage can depend on provider policy, traffic volume, sender eligibility, authentication, recipient privacy controls, and the provider's own filtering decisions.

Do not use FBLs as a source of truth for legal consent, unsubscribe state, or full recipient dissatisfaction. Your own mail system should remain authoritative for subscription state, suppression, bounces, and delivery telemetry.

Finally, treat every provider-specific parser and enrollment workflow as an integration boundary. Keep provider configuration, report parsing, and suppression logic modular so that a mailbox provider can change its endpoint, eligibility rules, or report format without forcing a redesign of the rest of the mail pipeline.
