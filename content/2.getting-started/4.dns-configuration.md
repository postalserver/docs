To work properly, Postal needs a number of DNS records for the Postal installation itself. This page covers **Postal infrastructure DNS**. DNS records for domains that Postal sends mail from are documented separately in [Sending domain configuration](sending-domain-configuration).

::callout{icon="i-heroicons-information-circle"}
The hostname used by Postal does not have to be the same as a sending domain. This guide uses `postal.example.com` as the canonical example because it matches the default Postal configuration. A deployment may use another stable hostname, such as `mail.example.com`, but changing the Postal hostname does not change the sending domain or any of the domain-derived DNS records.
::

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
**Do not confuse the example `postal` hostname label with configuration prefixes.** `postal.example.com` is the Postal installation hostname used in this guide. `dns.dkim_identifier`, `dns.domain_verify_prefix`, and `dns.custom_return_path_prefix` control different things and are not derived from the `postal` label. For example, `domain_verify_prefix: postal-verification` becomes part of a TXT value, not a hostname.
::

We'll assume for the purposes of this documentation you have both IPv4 and IPv6 available to your server. We'll use the following values in this documentation, you'll need to replace them as appropriate.

* `192.168.1.3` - IPv4 address
* `2a00:1234:abcd:1::3` - IPv6 address
* `postal.example.com` - the hostname you wish to use to run Postal

## A Records

You'll need these records for accessing the API, management interface and SMTP server.

| Hostname | Type | Value |
| --- | --- | --- |
| `postal.example.com` | A | `192.168.1.3` |
| `postal.example.com` | AAAA | `2a00:1234:abcd:1::3` |

Your Postal hostname can also be used as the MX target for domains that Postal receives mail for.

## MX records

The `dns.mx_records` setting contains the MX hostnames that Postal expects when it checks a domain's MX configuration. It accepts one or more hostnames.

For a single-node deployment, a single MX hostname is enough:

```yaml
dns:
  mx_records:
    - postal.example.com
```

For example, if Postal is also receiving mail for `example.com`, the DNS record would be:

```dns
example.com.    MX    10 postal.example.com.
```

If the domain receives mail through Postal, consider adding the inbound TLS hardening described in [Sending domain configuration](sending-domain-configuration), including MTA-STS and SMTP TLS Reporting. These controls are domain-level policies and are not part of the Postal `dns.*` configuration.

A multi-node installation may use separate hostnames:

```yaml
dns:
  mx_records:
    - mx1.postal.example.com
    - mx2.postal.example.com
```

with corresponding A/AAAA records for those hostnames.

::callout{icon="i-heroicons-information-circle"}
`mx1`, `mx2`, and additional MX hostnames are deployment choices, not Postal requirements. Do not create additional MX hostnames simply to match the example. Use the number and names of MX hosts that exist in your actual deployment.
::

::callout{icon="i-heroicons-exclamation-triangle"}
Do not change the MX records of an existing production domain merely because Postal is installed. If another mail service already receives mail for the domain, leave its MX records in place unless you intentionally want Postal to handle inbound mail.
::

## SPF Record

You can configure a global SPF record for your Postal installation so that sending domains do not need to list each Postal IP address individually. This makes future IP changes easier to manage.

Configure the SPF include hostname in `postal.yml`:

```yaml
dns:
  spf_include: spf.postal.example.com
```

Create the SPF record:

| Hostname | Type | Value |
| --- | --- | --- |
| `spf.postal.example.com` | TXT | `v=spf1 ip4:192.168.1.3 ip6:2a00:1234:abcd:1::3 -all` |

::callout{icon="i-heroicons-information-circle"}
The current Postal sample configuration uses `~all`, but Postal's DNS checker only requires an SPF record containing the configured `spf_include`. For a hardened production policy, use `-all` once every legitimate sender for this SPF host is covered. During a migration, `~all` may be used temporarily as a soft-fail policy.
::

## Return Path

The return path domain is the default domain used for the SMTP envelope `MAIL FROM` infrastructure. Configure it in `postal.yml`:

```yaml
dns:
  return_path_domain: rp.postal.example.com
```

Create the following records:

| Hostname | Type | Value |
| --- | --- | --- |
| `rp.postal.example.com` | A | `192.168.1.3` |
| `rp.postal.example.com` | AAAA | `2a00:1234:abcd:1::3` |
| `rp.postal.example.com` | MX | `10 postal.example.com` |
| `rp.postal.example.com` | TXT | `v=spf1 a mx include:spf.postal.example.com -all` |

Postal also needs a DKIM TXT record for the Return Path domain. Do not hard-code the selector from this example; generate the record using Postal:

```bash
postal default-dkim-record
```

Publish the exact hostname and value returned by that command. The selector depends on `dns.dkim_identifier`. Do not assume it is `postal._domainkey`; use the command output.

::callout{icon="i-heroicons-information-circle"}
The original documentation hard-coded `<DKIM selector>._domainkey.rp.postal.example.com` because the default `dkim_identifier` is `postal`. If you configure a different identifier, such as `dkim`, the selector changes. Use the output of `postal default-dkim-record` rather than copying the old hostname literally. This command provides the global Postal signing-key record used by the Return Path/fallback identity; it is not the domain-specific DKIM record for a sending domain.
::

::callout{icon="i-heroicons-information-circle"}
As with the infrastructure SPF record, `-all` is the hardened production policy. Use `~all` temporarily when migrating and when you still need a soft-fail policy.
::

## Route domain

If you wish to receive incoming e-mail by forwarding messages directly to routes in Postal, you'll need to configure a domain for this by pointing it to your Postal server using an MX record.

Configure:

```yaml
dns:
  route_domain: routes.postal.example.com
```

Then create:

| Hostname | Type | Value |
| --- | --- | --- |
| `routes.postal.example.com` | MX | `10 postal.example.com` |

This is optional and is not required for a sending-only Postal deployment.

## Click and Open Tracking

If you would like to make use of Click and Open Tracking, configure the Postal tracking hostname and the sending-domain tracking hostname separately.

Configure:

```yaml
dns:
  track_domain: track.postal.example.com
```

Create:

| Hostname | Type | Value |
| --- | --- | --- |
| `track.postal.example.com` | A | `192.168.1.3` |
| `track.postal.example.com` | AAAA | `2a00:1234:abcd:1::3` |

You must also configure a tracking domain such as `click.example.com` for the sending domain and point it to `track.postal.example.com`, then route that hostname through your web proxy as described in [Click & Open Tracking](/features/click-and-open-tracking).

::callout{icon="i-heroicons-exclamation-triangle"}
Publishing `track.postal.example.com` alone is not enough. Postal's tracking documentation requires the public tracking hostname to be on the same domain as the sender and to be routed through the Postal web server with the `X-Postal-Track-Host: 1` header.
::

## Example Postal Configuration

For a single-node installation using `postal.example.com` as both the Postal hostname and the configured MX hostname:

```yaml
version: 2

postal:
  web_hostname: postal.example.com
  web_protocol: https
  smtp_hostname: postal.example.com
  #use_local_ns_for_domain_verification: false

dns:
  mx_records:
    - postal.example.com
  spf_include: spf.postal.example.com
  return_path_domain: rp.postal.example.com
  route_domain: routes.postal.example.com
  track_domain: track.postal.example.com
  dkim_identifier: postal
  domain_verify_prefix: postal-verification
  #custom_return_path_prefix: psrp
  #timeout: 5
  #resolv_conf_path: /etc/resolv.conf
```

::callout{icon="i-heroicons-information-circle"}
The names above are examples. Keep the Postal infrastructure namespace stable after deployment. If you change a configured hostname or prefix later, update the corresponding DNS records and all dependent sending-domain records consistently.
::
