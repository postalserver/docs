This page contains information on how to identify problems with your installation.

## Logs

All Postal processes log to standard output, so the first place to look is the container logs:

```bash
postal logs            # all services
postal logs smtp       # just the SMTP server
postal logs worker -f  # follow the worker log
```

Each SMTP connection and each processed message is logged with a `trace_id` so you can grep for everything related to one connection. See [Logging](/features/logging) for the options that control how much is logged, including `smtp_server.log_connections` and the per-server **Log SMTP data** setting.

## Health checks

The worker and SMTP server each expose a small HTTP server (on ports 9090 and 9091 respectively, bound to localhost by default) with `/health` and Prometheus `/metrics` endpoints. `curl http://127.0.0.1:9090/health` should return `OK`. See [Health & Metrics](/features/health-metrics).

## Message activity

Every message in the web interface has an **Activity** (deliveries) tab listing each delivery attempt with the details and output received from the remote server or HTTP endpoint. This is usually the quickest way to find out why a message is delayed or has failed. The **Queue** page for a server shows everything waiting to be processed, including when the next retry is due.

## DNS

Whilst Postal can verify DNS records on its own, it can be useful to check what the rest of the internet is seeing.

You can make use of [Whats My DNS](https://whatsmydns.net) for a quick global check or the `dig` command if you have it on a terminal, i.e. `dig txt yourdomain.com` or `dig a yourdomain.com`.

Domain checks in Postal query the domain's own authoritative nameservers by default, so changes are usually seen straight away. If your server cannot reach external nameservers you can set `postal.use_local_ns_for_domain_verification: true` to use the resolvers from `/etc/resolv.conf` instead.

## SMTP

The quickest way to ensure the internet can connect to your Postal SMTP server is with `telnet postal.yourdomain.com 25`. You should see a banner beginning `220 postal.yourdomain.com ESMTP Postal/...`. You can proceed to attempt sending a message manually if you are familiar with the raw SMTP commands to further verify your Postal installation is working correctly. Remember that Postal requires `<CR><LF>` line endings; some telnet clients only send `<LF>`.

### SMTP SSL

If you aren't sure about whether the SSL certificate you have provided to Postal is set up correctly you can use `openssl s_client -connect postal.yourdomain.com:25 -starttls smtp` to get some information about your certificate from the point of view of SMTP.

## Postal's own e-mails

Postal sends e-mails to users for password resets, send limit warnings and server suspensions using the `smtp` section of its configuration. To check this works, run:

```bash
postal test-app-smtp you@example.com
```

If the message cannot be sent, the error and the SMTP settings in use are printed.

## Web interface

If you see `Blocked host` errors or the web interface refuses to load, check that `postal.web_hostname` matches the hostname you are using to access it. If open/click tracking domains show `Hello.` but tracked links return a Rails error page, make sure your proxy is sending the `X-Postal-Track-Host: 1` header for those hosts.
