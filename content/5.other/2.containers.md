This page contains information about how Postal actually is packaged and run within a container.

## Where's the container?

Postal is packaged and hosted at `ghcr.io/postalserver/postal`.

The `latest` tag will always track the `main` branch within the repository and therefore will have the latest copy of the application. It is not recommended to use this tag in production because you may start using it at any time without noticing.

Each version of Postal will also be tagged, for example, `3.3.7`. We always recommend using a version tag in production. To upgrade, you simply need to start using the newer version of the container and be sure to run the `upgrade` command. You can view all the tags which exist [on GitHub](https://github.com/postalserver/postal/pkgs/container/postal) and in [our CHANGELOG](https://github.com/postalserver/postal/blob/main/CHANGELOG.md).

The image is currently built for `linux/amd64` only.

## What processes need to run?

There are 3 processes that need to be running for a successful Postal installation. All processes are run within the same image (`ghcr.io/postalserver/postal`). The table below identifies the processes.

### The web server

- **Command:** `postal web-server`
- **Ports:** 5000

This is the main web server that handles all web traffic for Postal's admin interface, the HTTP API and open/click tracking requests. By default, it listens on `127.0.0.1:5000` but this can be configured in the `postal.yml` file by changing the `web_server.default_port` and `web_server.default_bind_address` options or setting the `PORT` and `BIND_ADDRESS` environment variables. The number of request threads is set by `web_server.max_threads` (default 5).

You can run multiple web servers and load balance between them to add additional capacity for web requests. The web server is expected to sit behind a TLS-terminating proxy; if that proxy is not on the same host, add its address to `postal.trusted_proxies`.

### The SMTP server

- **Command:** `postal smtp-server`
- **Ports:** 25 (plus 9091 for the [health server](/features/health-metrics))
- **Capabilities required:** `NET_BIND_SERVICE`

This is the main SMTP server for receiving messages from clients and other MTAs. As with the web server, you can configure this to run on any port by changing the `smtp_server.default_port` option in the `postal.yml` config file or setting the `PORT` environment variable. By default it listens on all IPv4 and IPv6 addresses (`::`).

You can run multiple SMTP servers and load balance between them to add additional capacity for SMTP connections. If your load balancer supports the HAProxy PROXY protocol (v1), you can enable `smtp_server.proxy_protocol` so that Postal sees the real client IP addresses.

### The worker(s)

- **Command:** `postal worker`
- **Ports:** 9090 for the [health server](/features/health-metrics)

This runs a worker which processes the message queue and delivers webhooks. Essentially, this handles processing all incoming and outgoing e-mail. Each worker runs a configurable number of threads (`worker.threads`, default 2). If you're needing to process lots of e-mails, you may wish to run more than one of these. You can run as many of these as you wish; they coordinate through the database. See [Workers & background tasks](/other/workers-and-background-tasks) for details.

## Other commands

The `postal` command inside the image also provides the following. In the standard installation these are run for you by the [`postal` helper script](/getting-started/postal-command) using a temporary `runner` container.

| Command | Description |
|---|---|
| `postal initialize` | Create the main database and load the schema. Run once on a new installation. |
| `postal upgrade` (or `postal update`) | Run pending database migrations on the main database and on every mail server's message database. Run after changing to a new version. |
| `postal make-user` | Interactively create a new global administrator user. |
| `postal default-dkim-record` | Print the DKIM TXT record for the return path domain, derived from your signing key. |
| `postal test-app-smtp address@example.com` | Send a test e-mail using the `smtp` section of the configuration (used for Postal's own notifications). |
| `postal version` | Print the version of Postal in the image. |
| `postal console` | Open an interactive Rails console. |

## Configuration

The image expects its configuration to be mounted at `/config`, and looks for `/config/postal.yml` (this path can be changed with the `POSTAL_CONFIG_FILE_PATH` environment variable). At a minimum, this directory should contain a `postal.yml` and a `signing.key`. You can see a minimal example `postal.yml` in the [installation tool repository](https://github.com/postalserver/install/blob/main/examples/postal.v3.yml). For a full example, [see here](https://github.com/postalserver/postal/blob/main/doc/config/yaml.yml).

Alternatively, every option can be provided as an environment variable, in which case no `postal.yml` is needed at all - see [Configuration](/getting-started/configuration#environment-variables). You will still need to mount the signing key and set `POSTAL_SIGNING_KEY_PATH` to its location.

The `signing.key` is an RSA private key used to sign webhook requests and as the DKIM key for the return path domain. It can be generated using the following command:

```
openssl genrsa -out path/to/signing.key 2048
```

## Networking

If you wish to utilise IP pools, you will need to run Postal using host networking. This is because Postal will need to be able to determine which physical IPs are available to it and be able to send and receive traffic on those IPs.

If you are not using IP pools, there is no need to use host networking and you can expose the ports listed above as appropriate.

## Waiting for services

The container's entrypoint supports waiting for external services to be ready before starting the underlying process. To use this you need to set the `WAIT_FOR_TARGETS` environment variable with a list of services and ports. For example, `mariadb:3306`, replacing `mariadb` with the hostname or IP of your MariaDB server. You can specify multiple endpoints by separating them with whitespace. Targets beginning with `http://` or `https://` are checked with an HTTP request (any `2xx` response counts as ready) rather than a TCP connection.

The default maximum time to wait is 30 seconds, you can override this using the `WAIT_FOR_TIMEOUT` environment variable. If a target is not available within the timeout the container exits with an error.

## Waiting for database migrations

When running in an orchestrated environment where migrations are run as a separate job at the same time as the application starts, enable the migration waiter so that web, SMTP and worker processes do not start until the schema is up to date:

```yaml
migration_waiter:
  enabled: true
  # Check up to this many times...
  attempts: 120
  # ...sleeping this many seconds between checks (default total: 4 minutes)
  sleep_time: 2
```

If migrations are still pending after all attempts, the process exits with status 1 so your orchestrator can restart it. The waiter is skipped for the console, rake tasks and the `postal upgrade` command itself.
